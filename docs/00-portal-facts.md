## 3. Задачи: поля, статусы, стадии

### 3.1 Статусы — их ПЯТЬ, а не семь

`tasks.task.getFields` → `STATUS` (enum) на этом портале:

| Код | Название |
|---|---|
| 2 | Ждёт выполнения |
| 3 | Выполняется |
| 4 | Ожидает контроля |
| 5 | Завершена |
| 6 | Отложена |

**Статусов 1 («Новая») и 7 («Отклонена») в перечислении нет.** Всё, что раньше
планировалось на «семь статусов Б24», переделывается под этот набор.

#### `STATUS` и `REAL_STATUS` — это разные вещи, и их легко перепутать

| На входе (фильтр) | В ответе | Что это |
|---|---|---|
| `REAL_STATUS` | `status` | **Настоящий статус** задачи (2–6) |
| `STATUS` | `subStatus` | Статус «для сортировки и фильтрации», куда дополнительно попадают **псевдостатусы**: `-1` просрочена, `-2` не просмотрена, `-3` почти просрочена |

Практическое следствие: `filter[STATUS]=3` **не вернёт** задачу, которая выполняется, но
просрочена — она уедет в `-1`. Для честной выборки по статусу использовать
`filter[REAL_STATUS]`. Для выборки просроченных достаточно `filter[STATUS]=-1`
(проще, чем связка `<DEADLINE` + `!REAL_STATUS`, которой пользовался спайк).

В кэше хранить оба поля: `status` (настоящий) и `sub_status` (мета).
То, что `REAL_STATUS` не появился в `getFields`, — особенность перечня полей, а не признак
отсутствия: как поле фильтра он документирован и работает.

### 3.2 «Новые» — это СТАДИЯ, а не статус

То, что пользователь видит в проекте как колонки канбана, живёт отдельно от `STATUS`:

```
task.stages.get(entityId=33)  →
  333 «Новые»        SYSTEM_TYPE=NEW   COLOR=00C4FB  ENTITY_TYPE=G
  335 «Выполняются»  SYSTEM_TYPE=null  COLOR=47D1E2
  337 «Сделаны»      SYSTEM_TYPE=null  COLOR=75D900
```

- Метод — `task.stages.get` (не `tasks.task.stages.get`, тот отвечает `ERROR_METHOD_NOT_FOUND`).
- `entityId` = ID группы, `ENTITY_TYPE='G'`.
- Стадии **у каждого проекта свои** — названия задаёт владелец проекта.
- `STATUS` и `STAGE_ID` независимы: задача `#197` имеет `status=2` (Ждёт выполнения) и
  `stageId=337` («Сделаны»). Задача `#193` — `stageId=0` (вне канбана).
- `filter[STAGE_ID]` в `tasks.task.list` работает.

**Следствие для сводки:** показывать только `STATUS` — значит показывать не то, что клиент
видит в Битриксе. Сводка должна строиться по стадиям проекта с фолбэком на статусы там,
где стадий нет.

| Фильтр | Результат |
|---|---|
| `filter[GROUP_ID]=11` | ✅ 27 задач |
| `filter[GROUP_ID][]=11&filter[GROUP_ID][]=21` | ✅ 38 задач (массив работает) |
| `filter[<DEADLINE]=<now>` + `filter[!=STATUS]=5` | ✅ 30 задач — просроченные |
| `filter[RESPONSIBLE_ID]=1` | ✅ 18 задач |
| `filter[>CHANGED_DATE]=<дата>` | ✅ 9 задач — **основа инкрементальной синхронизации** |
| `filter[%TITLE]=отчет` | ✅ 5 задач — поиск по подстроке |
| `filter[STAGE_ID]=337` | ✅ 2 задачи |

Пагинация: `total` приходит, `next=50`, **размер страницы жёстко 50 и не меняется**,
управление только через `start=(N-1)*50`.

Keyset (`start=-1`) на портале работает: возвращает страницу, `next=null` и `total=null` —
то есть режим «без подсчёта `COUNT`». Официальный приём для больших объёмов:
`order[ID]=asc` + `filter[>ID]=<последний>` + `start=-1`. В документации Битрикса замер на
2.4 млн записей: 49.9 с → 0.097 с. Комбинируется с `batch` (до 50 подзапросов по 50 записей
= 2500 задач за один HTTP-вызов), но помнить про лимит `operating` — batch его не обходит.

Для нашего кэша с отставанием 5 минут основной режим другой и дешёвый:
`filter[>CHANGED_DATE]=<последняя синхронизация>` + `order[CHANGED_DATE]=asc`.

## 4. Лимиты — ДВА независимых механизма

Замер: 30 последовательных вызовов за 4.69 с = 6.4 rps, ноль ошибок лимита.
Задержки: min 124 мс, среднее 155 мс, max 191 мс.

**Этот замер НЕ означает, что можно держать 6.4 rps.** Он означает, что мы уложились в
всплеск. Действуют два механизма одновременно:

### 4.1 Частота — leaky bucket

| Тариф | Утечка (устойчивая скорость) | Ёмкость (всплеск) |
|---|---|---|
| Enterprise | 5 запросов/с | 250 |
| Все прочие, включая наш | **2 запроса/с** | **50** |

При переполнении — HTTP 503 и `QUERY_LIMIT_EXCEEDED`. Максимальная длительность одного
запроса — 60 секунд. Наши 30 запросов за 4.69 с осели в ведре (накопилось ~20 из 50) и
поэтому прошли без ошибок; на длинной дистанции потолок — именно 2 rps.

**Лимитер: токен-бакет на портал, скорость 2/с, ёмкость 50, ретрай с backoff на 503.**

### 4.2 Ресурсоёмкость — operating time

Второй, независимый лимит: суммарное время выполнения методов в скользящем окне 10 минут
(десять поминутных корзин), по умолчанию **420 секунд**. Превышение — HTTP 429 и
`OPERATION_TIME_LIMIT`. Текущий расход приходит в блоке `time` каждого ответа:

```json
{"duration": 0.12, "processing": 0, "operating": 0, "operating_reset_at": 1786749854}
```

На нашем портале в момент замера `operating: 0`, окно сброса — 600 с (совпадает).

**batch от этого лимита НЕ спасает:** он экономит HTTP-вызовы и помогает против leaky bucket,
но `operating` считает время выполнения самих методов, а оно не уменьшается от упаковки.

**Итого лимитер строим по обоим осям:** токен-бакет 2/с с ёмкостью 50 плюс учёт `operating`
из каждого ответа с торможением при приближении к 420 с в окне.

`batch`: 5 команд за 228 мс, одним HTTP-вызовом. Ответ содержит `result`, `result_error`,
`result_total`, `result_next`, `result_time` по каждой команде отдельно. Ошибка одной команды
не роняет остальные.

### 5.1 Комментарии задач живут в чате, а не в форуме

Проверено записью 15.08.2026. На этом портале новая карточка задач, и комментарии — это
сообщения в **чате задачи**, а не записи форума:

```
task.commentitem.add(TASKID=205, FIELDS[POST_MESSAGE]=…)  → ID=10439   ✅ создался
task.commentitem.getlist(TASKID=205)                      → 0 записей  ❌
task.commentitem.get(TASKID=205, ITEMID=10439)            → ITEM_NOT_FOUND_OR_NOT_ACCESSIBLE
tasks.task.get(205).chatId                                → 1385
im.dialog.messages.get(DIALOG_ID='chat1385')              → 2 сообщения:
   id=10439 author=1  «Проба …»                     ← наш комментарий
   id=10437 author=0  «[USER=1]…[/USER] создал [URL=…]задачу[/URL]»  ← системное
```

**Что из этого следует:**

1. **Запись комментария** — `task.commentitem.add` работает, возвращаемый ID **равен ID
   сообщения в чате**.
2. **Чтение комментариев** — только `im.dialog.messages.get` по `DIALOG_ID='chat<chatId>'`.
   Значит `CHAT_ID` обязателен в `select` при чтении задачи, а scope `im` обязателен у приложения.
3. **`COMMENTS_COUNT` не заполняется** (`None` даже сразу после добавления комментария).
   Строку «Комментариев: N» в карточке бота либо считаем через `im`, либо не показываем.
4. `FORUM_TOPIC_ID` у задач `None` — старый форумный механизм не используется вовсе.
5. Системные события («создал задачу») тоже лежат в этом чате с `author=0` — при чтении
   комментариев их надо отфильтровывать, иначе они уедут в Telegram как чужие реплики.
6. Это же объясняет, почему `ONTASKCOMMENTADD` на новых карточках отдаёт `ID=0`, а настоящий
   идентификатор приходит в `MESSAGE_ID`.

**Проблема с учётом времени:** фильтры `task.elapseditem.getlist` не работают (`ERROR_CORE`),
поэтому отчёт по времени за период по проекту нельзя получить одним запросом.
Варианты: выкачивать весь список постранично и фильтровать у себя (79 записей на этом
портале — недорого, но растёт линейно), либо запрашивать по задачам через `batch`.
Решение принимаем при проектировании отчётов.

### 5.2 Учёт времени: постраничность СЛОМАНА, `ORDER` работает (проверено 18.08.2026)

| Что | Результат |
|---|---|
| `task.elapseditem.getlist` без параметров | 50 записей, конверт обещает `next: 50, total: 79` |
| то же с `start=50` | **снова та же первая страница** (первые ID `1, 3, 5`) — параметр игнорируется |
| то же с `start=100` | опять 50 записей той же страницы |
| `PARAMS[NAV_PARAMS][iNumPage]=2` и `NAV_PARAMS[iNumPage]=2` | **0 записей** |
| `ORDER[ID]=DESC` | ✅ работает, первый ID `177` вместо `1` |

То есть **больше 50 записей за раз метод не отдаёт ни одним известным способом**, хотя
`total` в конверте честно говорит, сколько их всего. Единственный рычаг — направление
сортировки: `ASC` даёт 50 самых старых, `DESC` — 50 самых свежих.

Отсюда правило отчёта: тянем обе стороны, объединяем по `ID` и **сравниваем размер
объединения с `total`**. Совпало — данные полные; не совпало — в отчёте обязана стоять
строка о том, сколько записей портал показал из скольких. Это единственная проверяемая
формулировка: по датам полноту не доказать, потому что запись можно завести задним числом.

Поля записи: `ID, TASK_ID, USER_ID, SECONDS, MINUTES, SOURCE, COMMENT_TEXT, CREATED_DATE,
DATE_START, DATE_STOP`. Считать надо по `DATE_START` — это когда работали, а `CREATED_DATE`
это когда занесли; при списании задним числом они расходятся.

**`TIME_SPENT_IN_LOGS` у задачи заполняется** и равен сумме её записей в секундах:
задача `#17` — `'18000'` (5 часов) при одной записи на 18000 секунд. У задачи без списаний
поле приходит `null`, а не `0`. Значит для суммы ПО ОДНОЙ задаче второй запрос не нужен.

**История задачи датирует списания:** `tasks.task.history.list` отдаёт записи
`{"field": "TIME_SPENT_IN_LOGS", "value": {"from": "0", "to": "18000"}}` с `createdDate`.
Это запасной источник, если когда-нибудь понадобится точность там, где `getlist` не
дотягивается: он читается через `batch` по задачам, но стоит одного вызова на задачу.

**`MINUTES` есть на выходе и запрещён на входе.** В ответе `getlist` поле присутствует
всегда (`"SECONDS": "900", "MINUTES": "15"`), и это ровно та ловушка, что описана в §1:
имена полей ответа нельзя переиспользовать для запроса. Портал сам делит на 60.

**`COMMENT_TEXT` — не BBCode.** Отправили `спайк [проверка] BBCode`, вернулось дословно,
со скобками. Значит `esc_bbcode()` здесь применять НЕЛЬЗЯ: он заменил бы скобки на
полноширинные и испортил бы текст, который портал и так не разбирает. Это единственное
известное исключение из «все подстановки в Битрикс — через `esc_bbcode`»; экранирование
для Telegram (`esc_html`) при показе той же строки обратно в чат обязательно.

**`TIME_SPENT_IN_LOGS` обновляется сразу же:** `null` → `'1500'` после двух записей на
600 и 900 секунд, без задержки и без отдельного пересчёта.

### 5.4 Дозапись тега — только read-modify-write

`tasks.task.update` с `fields[TAGS]` задаёт **полный набор тегов задачи**, а не добавляет
к существующим. Проверено там же: у `#231` был тег идемпотентности `tgapp-1-6afecad7…`,
после `TAGS=[исходный, "tg-support"]` стало два, после `TAGS=[исходный]` — снова один.

Отсюда правило: чтобы дописать тег, надо сперва прочитать `TAGS` задачи и отправить
объединение. Отправка одного лишь нового тега **стирает ключ идемпотентности** и ломает
И-10 — повторная отправка того же сообщения создала бы дубль задачи.

`filter[TAG]` работает **вместе с** `filter[GROUP_ID]`: связка
`{"GROUP_ID": [35], "TAG": "tg-support"}` вернула ровно ту задачу, что была помечена,
а несуществующий тег — `0` задач и `total=0`. На этом строится фильтр отчёта о
трудозатратах: отбор идёт на портале, а не перебором у себя.

## 11. SPIKE E — события (проверено 16.08.2026)

Приложению доступно **220 событий**, из них про задачи ровно шесть: `ONTASKADD`,

### 11.1 Тело события

```
ts, event, event_handler_id
auth[domain], auth[member_id], auth[status], auth[scope]
auth[user_id]            ← КТО совершил действие
auth[access_token] (70), auth[expires], auth[expires_in]
auth[application_token]  ← ТО ЖЕ значение, что при установке
auth[client_endpoint] = https://devondev.bitrix24.ru/rest/

data[FIELDS_BEFORE][ID], data[FIELDS_AFTER][ID]
data[IS_ACCESSIBLE_BEFORE], data[IS_ACCESSIBLE_AFTER]
data[FIELDS_AFTER][TASK_ID], data[FIELDS_AFTER][MESSAGE_ID]   ← только у комментариев
```

**`auth[user_id]` есть.** Атрибуция «кто изменил» доступна без дозапроса — открытый
вопрос плана закрыт.

**`data[FIELDS_AFTER]` содержит ТОЛЬКО `ID`.** Никаких изменённых полей, никакого diff.
Это переводит кэш задач из разряда оптимизации в **обязательную подсистему**: без него
невозможно понять, что именно поменялось, и невозможно сообщить об удалении задачи —
дозапрашивать уже нечего.

**`auth[application_token]` в событии совпадает с полученным при установке** — то есть
им действительно можно опознать портал, но нельзя доказать, что запрос пришёл от Битрикса
(инвариант И-8). Событие приносит и рабочий `auth[access_token]`, но пользоваться токеном
из тела недоверенного запроса нельзя: ходим только своим сохранённым.

### 11.2 Системные сообщения порождают события о комментариях

Замер на одной тестовой задаче: создание → переименование → перевод в работу →
комментарий → удаление дали **7 событий**:

| Время | Событие | Задача | MESSAGE_ID | `auth[user_id]` |
|---|---|---|---|---|
| 08:50:58 | `ONTASKCOMMENTADD` | 207 | 10483 | **пусто** |
| 08:50:58 | `ONTASKADD` | 207 | — | 1 |
| 08:51:02 | `ONTASKUPDATE` | 207 | — | 1 |
| 08:51:05 | `ONTASKUPDATE` | 207 | — | 1 |

Из трёх `ONTASKCOMMENTADD` **настоящий комментарий только один**. Два других —

3. Уведомление о комментарии отправляется только после дозапроса, подтвердившего, что
   сообщение существует и относится к нашему проекту.
4. Событие не говорит, что изменилось: сравнение делаем с `task_cache`.

на верхнем уровне: **терять строку нельзя**, иначе список молча короче, чем в Битриксе.

## 13. Поля задачи для опросника (проверено 16.08.2026)

`tasks.task.getFields` отдаёт **67 полей**. `task.item.userfield.getlist` — 5 UF-полей,
из них на этом портале два содержательных: `UF_AUTO_01769682BFCF` («Приоритет», string)
и `UF_AUTO_80FB9545CBCF` («Тип», string). Остальные три — служебные (`UF_CRM_TASK`,
`UF_TASK_WEBDAV_FILES`, `UF_MAIL_MESSAGE`).

**Подписи полей есть только у `getFields`.** У `userfield.getlist` `EDIT_FORM_LABEL`
приходит пустым, поэтому список для человека строится по `getFields`, а `getlist`
годится лишь для типа поля.

### 13.1 `values` у enum приходит в двух разных формах

| Поле | Форма `values` |
|---|---|
| `PRIORITY` | словарь: `{"2": "Высокий", "1": "Средний", "0": "Низкий"}` |
| `STATUS` | словарь: `{"2": "Ждёт выполнения", …}` |
| `MARK` | словарь: `{"N": "Отрицательная", "P": "Положительная"}` |
| `DURATION_TYPE` | **плоский список**: `["secs", "mins", "hours", …]` |

Разбор, рассчитанный на словарь, падает на `DURATION_TYPE` с
`'list' object has no attribute 'items'`. Поймано на живом портале.
Обрабатывать нужно обе формы (`b24/fields.py::_values_of`).

### 13.2 UF-поля пишутся при создании задачи и переживают перечитку

`tasks.task.add` с `UF_AUTO_01769682BFCF="Критично"` сохраняет значение. То же через
`tasks.task.update`. Молчаливого игнорирования тут нет — в отличие от неизвестных полей.

**Регистр на чтении сюрпризный.** `UF_AUTO_01769682BFCF` возвращается как
`ufAuto01769682bfcf`, а НЕ `ufAuto01769682BFCF`: каждый сегмент между подчёркиваниями
приводится к нижнему регистру, и только первая буква сегмента поднимается — а сегмент,
начинающийся с цифры, не поднимается вовсе. Угадывать этот ключ нельзя: задача читается
целиком, а поле берётся регистронезависимым поиском.

### 13.3 Что реально годится под ответ человека

Из 67 полей в allowlist попали пять стандартных — `TITLE`, `PRIORITY`, `DEADLINE`,
`TIME_ESTIMATE`, `TAGS` — плюс UF-поля подходящих типов. `DESCRIPTION` исключено
намеренно: это тело задачи, туда уходят ответы **без** привязки. `FORUM_TOPIC_ID`
и подобное в выпадающем списке настройщика — не гибкость, а способ сломать задачу.

`RESPONSIBLE_ID`, `ACCOMPLICES`, `AUDITORS`, `STAGE_ID` в списке нет: им нужен выбор
человека или стадии, а не текст. Появятся вместе с соответствующими виджетами.

Проверено сквозным прогоном (задача #215): выбор «Горит» лёг в `PRIORITY=2`,
текст «через 2 дня» — в `DEADLINE=2026-08-18T18:00:00+03:00`, остальные ответы — в тело,
тег идемпотентности уцелел рядом с тегами из ответов, повтор не создал дубль.

## 14. Создание пользовательских полей задачи (проверено 16.08.2026)

`task.item.userfield.add` работает под OAuth-приложением и возвращает **только числовой ID**
созданного поля, без объекта.

```
PARAMS: {
  FIELD_NAME: "UF_SD_SISTEMA",          # только [A-Z0-9_], подпись отдельно
  USER_TYPE_ID: "string" | "enumeration" | ...,
  EDIT_FORM_LABEL: {"ru": "Система"},   # именно словарь по языкам
  LIST: [{"VALUE": "Битрикс24"}, ...]   # только для enumeration
}
```

**Поле создаётся для ВСЕХ задач портала.** `ENTITY_ID` у него `TASKS_TASK` — привязки
к проекту или группе не существует. Пользователю это нужно сказать до нажатия кнопки,
иначе он уверен, что настраивает один проект.

Имя занято → `ERROR_CORE`: «Поле UF_X для объекта TASKS_TASK уже существует».
`task.item.userfield.delete` по ID работает и возвращает `true`.

### 14.1 Главная ловушка: в enum-поле уходит ID элемента, а не подпись

| Что записали в `UF_..._ENUM` | Что прочиталось |
|---|---|
| `"325"` (ID элемента) | `"325"` ✅ |
| `"Горит"` (подпись элемента) | `"0"` ❌ **молча** |

Ошибки нет, задача создаётся, поле выглядит заполненным до тех пор, пока не откроешь
карточку. Поэтому варианты ответа в опроснике хранят `value` = ID элемента, а подпись —
отдельно, для кнопки и для тела задачи.

### 14.2 Варианты списка не видны в `getFields`

Для UF-поля типа `enumeration` `tasks.task.getFields` отдаёт только
`{"title": ..., "type": "enumeration"}` — **ни одного варианта**. Список с ID лежит
в `task.item.userfield.getlist` → `LIST: [{ID, VALUE, SORT, DEF, XML_ID}]`.
Значит, за списком значений нужно ходить вторым методом; одного `getFields` мало.

### 14.3 Варианты досоздаются через `update` полным списком

```
task.item.userfield.update(ID=721, PARAMS={LIST: [
  {ID: "325", VALUE: "Горит"},      # существующие — с ID, иначе исчезнут
  {ID: "327", VALUE: "Обычное"},
  {VALUE: "Можно позже"},           # новый — без ID
]})
```

Возвращает `true`, существующие элементы сохраняют свои ID, новый получает следующий.
Передавать нужно **весь** список: это замена, а не добавление.

## 16. Адрес задачи на портале (проверено 18.08.2026)

REST не отдаёт адрес задачи ни одним методом — его собираем сами. Портал понимает две формы,
личную и групповую:

```
https://<портал>/company/personal/user/<user_id>/tasks/task/view/<task_id>/
https://<портал>/workgroups/group/<group_id>/tasks/task/view/<task_id>/
```

Проверено **без авторизации**: обе формы портал разбирает своим `urlrewrite` и кладёт разобранный
хвост в параметр `any=` редиректа на `auth2.bitrix24.net`:

```
/company/personal/user/1/tasks/task/view/233/ → 302 …&any=user%2F1%2Ftasks%2Ftask%2Fview%2F233%2F
/workgroups/group/6/tasks/task/view/233/      → 302 …&any=group%2F6%2Ftasks%2Ftask%2Fview%2F233%2F
/nonsense/path/that/does/not/exist/           → 302 …  (параметра any= нет вовсе)
```

То есть опознанный маршрут отличается от выдуманного, и это видно, не заходя на портал под
логином. Несуществующий `user_id` (9999) разбирается так же: пользователь в адресе — контекст
раздела, а не проверка прав, доступ к самой задаче портал проверяет отдельно.

**Берём личную форму** (`views.portal_task_url`, `views.task_ref`): её же Битрикс24 ставит
в собственные уведомления, поэтому её наверняка ловит мобильное приложение. Подставляется тот,
кто ближе к читателю: в карточке и списке — он сам, в уведомлении в чат — ответственный
по задаче, в личном сообщении — его получатель. Без домена или без пользователя ссылки не
выйдет — тогда остаётся обычный номер: пропасть он не имеет права, по нему открывают карточку
и его набирают в `/comment`.

## 17. Экран согласия `/oauth/authorize/` (проверено 27.08.2026)

Нужен для привязки в направлении **Telegram → портал** (docs/30-bot-spec.md §6.1.1).
Проверено **без авторизации**, с боевым `client_id` локального приложения:

```
GET https://devondev.bitrix24.ru/oauth/authorize/?client_id=local.6a8177faa0f811.94612504
    &response_type=code&state=probe
→ 302 https://auth2.bitrix24.net/oauth/authorize/?…&oauth_proxy_params=<base64>
```

Что из этого следует:

1. **Путь существует и у локального приложения**, отдельной регистрации «под OAuth» не
   требует: портал сразу уводит незалогиненного на вход Битрикс24.Net.
2. **Наши параметры переживают логин.** `oauth_proxy_params` — это base64 от
   `client_id=…&response_type=code&state=probe`, то есть `state` возвращается к нам ровно
   таким, каким отправлен. На нём и построена привязка.
3. **Незалогиненный ответ ничего не говорит о валидности `client_id`.** Выдуманный
   `local.nonexistent.00000000` даёт точно такой же 302. Проверка происходит после входа,
   поэтому по ответу без авторизации нельзя ни подтвердить, ни опровергнуть регистрацию
   приложения — и нельзя использовать этот запрос как проверку живости.
4. **`redirect_uri` через прокси логина тоже переносится**, но принимает ли его локальное
   приложение — по-прежнему неизвестно: это видно только после входа человеком.
   Поэтому по умолчанию мы его **не передаём** (`B24_OAUTH_REDIRECT=false`), а `code`
   принимаем на всех трёх путях, куда портал может его привезти
   (docs/50-web-and-b24-app.md §2.10).

Что проверяется одним живым входом и до сих пор не проверено: на какой именно путь портал
вернёт `code` и какие параметры при этом положит в query.
