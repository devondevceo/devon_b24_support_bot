# Архитектура и инфраструктура

Ключевое ограничение, из которого следует почти всё остальное: сервис живёт на **уже занятом
сервере**, где кроме Traefik, `devon-website`, `mclick_landing` и `devon-billing` крутится
ещё около восьми десятков контейнеров. У соседей нет ни `mem_limit`, ни `cpus`. Мы приходим
в чужой дом и обязаны вести себя тише хозяев. Второе ограничение: разработка идёт **сразу на
этом же боевом сервере** (решение заказчика, компенсирующие меры — в [70-plan.md](70-plan.md) §8).

## 0. Фактические ресурсы сервера

Замер 15.08.2026 на `test01`:

| Показатель | Значение | Комментарий |
|---|---|---|
| CPU | **6 ядер** | не 4, как предполагалось изначально |
| RAM | **11 ГБ**, занято 4.2, доступно **6.5** | не 8 ГБ |
| Swap | 4 ГБ, **занято 2.2** | при 6.5 ГБ свободной RAM это след прошлой нехватки памяти |
| Диск | 119 ГБ, занято 60, свободно **53** | места достаточно |
| Контейнеров | **85**, из них активных 84 | машина плотно занята |
| Образы Docker | 32.9 ГБ, **из них мусора 31.6 ГБ (96%)** | |
| Build-кэш | 10.4 ГБ, **мусора 10.0 ГБ** | |
| Volumes | 94, активных 33, 8.5 ГБ | 61 неиспользуемый — **трогать нельзя**, см. ниже |

**Наш стек (~2.1 ГБ) в 6.5 ГБ доступной памяти помещается с запасом.** Ресурсных
ограничений на контейнеры это не отменяет: 84 соседних контейнера без лимитов — ровно та
ситуация, ради которой лимиты и нужны.

**Занятый своп при свободной памяти** означает, что нехватка памяти на этой машине уже
случалась. Ядро вытеснило страницы и не вернуло их. Это аргумент не расслабляться с
`mem_limit`, а не наоборот.

**Освободить ~41 ГБ можно двумя безопасными командами** (`docker builder prune -af` и
`docker image prune -a`). **`docker volume prune` запускать нельзя ни при каких
обстоятельствах**: 61 неактивный volume может содержать данные остановленных контейнеров
соседних проектов, и восстановить их будет неоткуда. То же про `docker system prune --volumes`.

## 1. Состав контейнеров

| Контейнер | Что делает | RAM | CPU |
|---|---|---:|---|
| `b24bot-postgres` | PostgreSQL 16, данные + очередь + шина через `LISTEN/NOTIFY` | 1200 МБ | `cpu_shares: 512` |
| `b24bot-bot` | aiogram 3, приём апдейтов всех ботов теннантов, вся логика чата | 320 МБ | `cpu_shares: 512` |
| `b24bot-api` | FastAPI: `/api/v1/*` для панели, `/b24/*` для приложения и событий, отдача статики панели | 256 МБ | `cpu_shares: 512` |
| `b24bot-worker` | Синхронизация, события, outbox, отчёты, ротация ключей, уборка | 320 МБ | `cpu_shares: 512` |
| | **Итого наших** | **~2.1 ГБ** | |

**Redis нет.** Его роль закрывает PostgreSQL: очередь — таблицы `outbox` и `b24_event_inbox`,
пробуждение воркера — `LISTEN/NOTIFY`, состояние диалогов — `tg_fsm_states`, лимитеры —
`b24_portal_budget` и `tg_chat_budget`. Тот же приём применён в `mclick` и работает. Цена —
чуть больше нагрузки на БД; выгода — минус контейнер, минус 150–300 МБ и минус одна точка
отказа на машине, где памяти и так нет.

**Локальный Telegram Bot API сервер не ставим.** Каждый залогиненный бот — отдельный
инстанс TDLib, память растёт линейно от числа теннантов, а рабочий каталог копит скачанные
файлы. Остаёмся на облачном API с лимитом 20 МБ, как решил заказчик.

### Дисковый бюджет

Считаем явно, потому что при исчерпании диска PostgreSQL не деградирует, а падает с `PANIC`
и уходит в recovery, унося соседей по IO:

| Что | Объём |
|---|---:|
| Образы `python:3.12-slim` с зависимостями × 3 тега (текущий, откат, dangling) | 1.5–1.8 ГБ |
| `postgres:16-alpine` | 250 МБ |
| Build-кэш | 0.5–1 ГБ |
| Volume БД (20 теннантов, год) | ~3.5 ГБ |
| Бэкапы: 7 ежедневных + 4 еженедельных | 2–3 ГБ |
| `/data/tmp` под вложения | **tmpfs, `size=512m`** — жёсткая граница |
| Логи `json-file`, `max-size=10m max-file=3` × 4 контейнера | 120 МБ |
| **Итого** | **8–10 ГБ** |

`docker builder prune --filter until=168h` в конце каждого деплоя. Алерт на 80% заполнения
диска в `/health`. Первая команда проекта — `df -h`.

## 2. Приём Telegram: один процесс, много ботов

У каждого теннанта свой бот. Все они обслуживаются одним процессом `b24bot-bot`.

```
POST /tg/{webhook_id}          webhook_id — UUID из tg_bots, не угадывается
  → заголовок X-Telegram-Bot-Api-Secret-Token сверяется с tg_bots.webhook_secret
  → resolve_bot_by_webhook_id() — SECURITY DEFINER функция, не роль с BYPASSRLS
  → апдейт передаётся в Dispatcher с нужным экземпляром Bot из BotRegistry
```

- **Ответ всегда `200`,** и при неизвестном `webhook_id`, и при неверном секрете. Разница —
  только в метрике и в `security_log`. Иначе эндпоинт становится оракулом существования бота.
- `allowed_updates`: `message`, `edited_message`, `callback_query`, `my_chat_member`,
  `chat_member`. `message_reaction` **не запрашиваем** — ни один сценарий его не использует,
  а это лишний входящий трафик на машине с жёстким лимитом.
- IP-allowlist подсетей Telegram — middleware `ipAllowList` в Traefik, а не разбор
  `X-Forwarded-For` в приложении (заголовок подделывается).

### Транспорт Telegram: polling через SOCKS5, вебхук мёртв

**Проверено на боевом сервере 16.08.2026. Фильтрация двусторонняя:**

| Направление | Результат |
|---|---|
| Сервер → `api.telegram.org` | ❌ таймаут соединения |
| Серверы Telegram → `b24sdbot.devondev.ru` | ❌ `getWebhookInfo`: `Connection timed out`, в логах приложения ноль запросов на `/tg/` |
| Сервер → `api.telegram.org` **через SOCKS5** | ✅ ответ за 0.5 с |

Поэтому режим по умолчанию — **long polling**, а не вебхук. Тот же вывод, к которому пришёл
`mclick`, и тот же прокси.

**Схема `socks5h`, а не `socks5`.** Разница в том, кто резолвит имя. При `socks5://` клиент
резолвит `api.telegram.org` локально и получает заблокированный адрес — соединение уходит
в таймаут. При `socks5h://` имя уезжает прокси, и он резолвит сам. Замерено: `socks5h` —
401 за 0.5 с, `socks5` — таймаут 20 с. Нормализация схемы делается в `Settings.tg_proxy`,
чтобы человек не мог ошибиться при настройке.

**HTTP-таймаут обязан превышать длительность long polling.** `getUpdates` с `timeout=25`
держит соединение 25 секунд; при клиентском таймауте 20 секунд httpx рвёт связь раньше
ответа, и цикл вырождается в бесконечную серию таймаутов. Ровно это и случилось при первом
запуске. Считается в `tg.http_timeout_for()`.

Обработчик вебхука `/tg/{webhook_id}` из кода **не убран**: он заработает без единой правки,
если сервис переедет на хост с прямым доступом. Переключение — колонкой `tg_bots.mode`.

Прокси применяется **только к трафику Telegram**. Битрикс ходит напрямую: его домены
из России доступны.

Монитор `getWebhookInfo` раз в 10 минут актуален только в режиме вебхука: если URL не наш —
это компрометация токена, бот переводится в `suspended`, алерт суперадмину.

### Инвариант И-1: сырой апдейт не попадает в БД

Privacy mode выключен, бот видит всю переписку. Если положить `Update` целиком в очередь,
вся переписка сотрудников клиента окажется в таблице, в WAL и в бэкапах с ретенцией недели.
Поэтому апдейт обрабатывается **синхронно в процессе бота**, а в очередь уходят только
производные команды с идентификаторами. Тексты живут в памяти процесса до конца обработки.

Да, это значит, что при рестарте необработанный апдейт теряется. Это осознанный размен:
Telegram повторит доставку вебхука, а 152-ФЗ повторить нельзя.

Проверяется канареечным тестом: уникальная строка, отправленная в чат, не должна находиться
полнотекстовым поиском ни в одной таблице БД.

## 3. Клиент Битрикс24

### Лимитер: две независимые оси

Разведка ([00-portal-facts.md](00-portal-facts.md) §4) показала, что механизма два:

```python
# ось 1 — частота: leaky bucket, 2 запроса/с, ёмкость 50
# ось 2 — ресурсоёмкость: operating, 420 с в скользящем окне 600 с
```

Состояние — в `b24_portal_budget`, одна строка на теннанта. После **каждого** ответа читаем
блок `time` и обновляем `operating_spent` / `operating_reset_at`. При приближении к 420 с
переходим в режим «только интерактивные запросы», фоновая синхронизация ждёт.

**`batch` помогает против первой оси и не помогает против второй.** Он экономит HTTP-вызовы,
но `operating` считает время выполнения самих методов.

Две полосы движения:
- **интерактивная** — то, что ждёт живой человек в чате: приоритет, обходит очередь;
- **фоновая** — синхронизация, отчёты, дозапрос чужих задач: уступает всегда.

Ретраи: `503 QUERY_LIMIT_EXCEEDED` и `429 OPERATION_TIME_LIMIT` — экспоненциальный backoff
с джиттером. Таймаут одного запроса — 60 секунд (потолок Битрикса).

### Пагинация

- Инкремент кэша: `filter[>CHANGED_DATE]` + `order[CHANGED_DATE]=asc`. Дёшево, объём страниц
  минимальный.
- Первичный импорт: `order[ID]=asc` + `filter[>ID]=<последний>` + `start=-1` (отключает
  `COUNT`, который и есть главный тормоз), упаковано в `batch` по 50 подзапросов.
- Размер страницы фиксирован — 50, не настраивается.

### Обновление токена — единственная правильная реализация

```sql
SELECT pg_advisory_xact_lock(hashtextextended($tenant_id::text || ':' || $b24_user_id::text, 0));
```

**Только транзакционный лок.** Сессионный `pg_advisory_lock` с `finally: unlock` в asyncio
ломается: между взятием лока и входом в `try` возможна отмена задачи, лок остаётся висеть
на соединении, соединение возвращается в пул, и все последующие обновления этого токена
упираются в `lock_timeout`. Триггерится обычным флудом. Транзакционный лок освобождается
на `COMMIT`/`ROLLBACK`, отменить его между «взял» и «отпустил» невозможно.

Порядок действий под локом:
1. Перечитать токен. Если он уже свежий — ничего не делать, вернуть его.
2. Обменять `refresh_token`. **Он одноразовый:** обменяли — старый мёртв.
3. Если в ответе есть `error` — **ничего не записывать**, перевести привязку в `needs_reauth`,
   уведомить. Типовой баг чужих SDK — вычистить `error` и сохранить мусор как валидные данные.
4. `UPDATE ... WHERE token_version = $v RETURNING *`. **Ноль строк = инцидент:** мы сожгли
   refresh и не сохранили результат. Немедленно `needs_reauth` и запись в `security_log`,
   а не молчаливый возврат токена.
5. При `lock_timeout` — fail-closed: ошибка пользователю «попробуйте ещё раз». Никакого
   «пойдём обновлять без лока».

Джоб `warm_tokens` раз в 7 дней прогревает неактивные привязки: документация обещает
180 дней жизни `refresh_token`, полевые публикации — 28. Проектируем на худший случай.

### Egress-allowlist

Сервису разрешено ходить **только** на `*.bitrix24.ru`, `*.bitrix24.com`,
`oauth.bitrix24.tech`, `oauth.bitrix.info`, `api.telegram.org` (и прокси, если он появится).
Приватные диапазоны запрещены в резолвере.

**Хосты никогда не берутся из входящих данных.** `SERVER_ENDPOINT` в placement-POST формирует
браузер пользователя портала — то есть их полностью контролирует любой сотрудник теннанта.
Подмена увела бы `client_id`, `client_secret` и `refresh_token` на чужой сервер, а через
`client_endpoint` дала бы SSRF во внутреннюю сеть VPS, где живёт чужой прод.
`client_endpoint` собираем сами: `https://<tenants.b24_domain>/rest/`. Входящее значение
сравниваем и при расхождении пишем инцидент, а не применяем.

### Кто чьим токеном ходит

| Операция | Токен |
|---|---|
| Создание, редактирование задачи, комментарий | **Личный токен действующего пользователя** |
| Наполнение кэша задач, синхронизация проектов и стадий, приём событий | **`service_admin`** — токен установщика приложения |
| `event.bind`, `placement.bind`, `app.info`, установка | **`service_admin`** |

Отдельная сервисная учётка `service_reader` **отменена решением заказчика 16.08.2026**
(лицензию не выделяем). Фоновая работа идёт токеном администратора портала.

**Следствие для кода, а не для документации.** Раз Битрикс больше не режет видимость за нас,
изоляция между клиентами держится исключительно на наших фильтрах. Поэтому:

- слой доступа к задачам принимает список разрешённых `GROUP_ID` **обязательным аргументом**,
  а не опциональным фильтром: вызов «дай задачи» без области видимости не должен
  компилироваться в принципе;
- отбойники чужих задач (`task_cache.is_ours = false`) хранят только идентификатор и флаг,
  без заголовка и полей;
- тест изоляции двух клиентов одного теннанта входит в обязательный набор CI.

Подробности и полный список компенсирующих мер — [40-security.md](40-security.md) §1.

| `sync_tasks_initial` | однократно | Первичный импорт keyset + batch, `sync_state.phase='initial'` — уведомления подавлены |

| `reminders.digest` | 15 мин | утренняя сводка тем чатам, у кого наступило местное 9:00 |

**Что из этой таблицы реально работает на 25.08.2026:** `sync_stages`, `cleanup` и три
прохода напоминаний (`domain/reminders.py`, спецификация — docs/30-bot-spec.md §15).

**Добавлено 30.08.2026 (`domain/lifecycle.py`, проход раз в час):** `reconcile_events`
из таблицы выше реализован — суточная сверка подписок через `event.get` с досозданием
недостающих; тем же проходом перечитывается `app.info` (подписка Маркета, не чаще раза
в 20 часов на теннанта, не больше 5 теннантов за проход) и стираются данные теннантов,
у которых прошло 30 дней после деинсталляции. `cleanup` дополнительно держит ретенцию
`b24_call_log` (3 суток, требование Маркета).
Расписание проходов лежит в памяти процесса, как `_failed_until` в `domain/sync.py`:
перезапуск воркера просто проверит всё заново, а второго сообщения от этого не будет —
за это отвечают отметки `reminder_marks` в базе.

Джоб `check_overdue` из таблицы намеренно не делался отдельно: «пересечение дедлайна»
теперь живёт строкой «Просрочено» в утренней сводке, а личное предупреждение приходит
ДО срока, а не после. Уведомлять человека о том, что срок уже пропущен, — значит
приходить, когда сделать уже ничего нельзя.

**Что из этой таблицы реально работало на 16.08.2026:** только `sync_stages` и `cleanup`.
Проход по стадиям живёт в цикле воркера (`domain/sync.py`): раз в 15 минут он спрашивает
базу, у каких активных проектов `projects.stages_synced_at` старше суток, и обновляет
не больше пяти за раз. Портал — источник правды: переименованная колонка переезжает
в `project_stages`, исчезнувшая удаляется. **Пустой ответ портала справочник не трогает** —
это «портал промолчал», а не «колонок больше нет», и стереть по нему стадии значит
превратить всю сводку проекта в строку «Вне канбана».

Второй вход в ту же синхронизацию — сводка. Увидев у задачи стадию, которой нет
в справочнике, она обновляет стадии этого проекта на месте (не чаще раза в 10 минут
на проект) и пересчитывает строки. Иначе колонка, заведённая утром, до завтрашнего
прохода числилась бы «вне канбана».

Кнопка «Обновить» в чате форсирует синхронизацию, но **не чаще раза в 30 секунд на чат** —
иначе она превращается в оружие против бюджета портала, общего с другими интеграциями клиента.

Целевое отставание — 5 минут: 3 минуты опроса плюс запас на обработку.

### Переход `initial` → `steady`

Пока `sync_state.phase='initial'`, уведомления в чат подавлены. Иначе при подключении портала
с сотней просроченных задач весь накопленный хвост хлынет в чат одним залпом.

## 5. Приём событий Битрикса

```
POST /b24/events
  → member_id → resolve_tenant_by_member_id()
  → constant-time сверка application_token
  → вставка в b24_event_inbox с dedup_key
  → 200 немедленно, обработка асинхронно
```

**`APPLICATION_TOKEN` — идентификатор портала, а не доказательство подлинности.** Он приходит
в placement-POST, который выполняет браузер пользователя: любой сотрудник теннанта, включая
экстранет-пользователя клиента, читает его через F12. Из этого следуют жёсткие правила:

1. **Ни одно деструктивное действие не выполняется по событию.** `ONAPPUNINSTALL` только
   помечает подозрение; факт проверяется реальным вызовом `app.info` нашим сохранённым
   токеном (мёртвый токен = подтверждение). Иначе теннанта отключает один HTTP-запрос.
2. `dedup_key` считается **из данных дозапроса**, а не из тела события — иначе заранее
   вставленный ключ гасит настоящее событие.
3. Уведомление в чат уходит **только после успешного дозапроса**, подтвердившего изменение.
4. IP-allowlist подсетей Битрикса на `/b24/events` в Traefik.
5. Жёсткая квота на теннанта: при превышении N строк `pending` отвечаем `200` и считаем
   метрику, но не вставляем. 20 rps × сутки = 1.7 млн строк JSONB, диск общий с чужим продом.

### Отрицательный кэш

Фильтрации подписки по группе в Битриксе **не существует** — приходят события всех задач
портала. Каждое неизвестное `task_id` требует дозапроса только чтобы узнать `GROUP_ID` и
выбросить событие. Без отбойников (`task_cache.is_ours=false`, TTL 7 дней) мы тратим
большую часть квоты портала на чужие задачи и ломаем другие интеграции теннанта.
Дозапрос неизвестных ID — только батчем до 50 и только по фоновой полосе.

### Что ломается молча

Три механизма отказывают с чистыми логами. Все три закрываются в фазе 1:

1. **`APPLICATION_TOKEN` меняется при `ONAPPUPDATE`.** Не перезаписали — наша же проверка
   начинает отбрасывать все события теннанта. Обработчик `ONAPPUPDATE` перезаписывает токен
   и заново вызывает весь набор `event.bind`. Покрыто отдельным тестом.
2. **Обработчики событий удаляются при обновлении приложения.** Суточный `reconcile_events`
   досоздаёт недостающие, обязательно токеном администратора — не-админ получит неполный
   список, и мы решим, что подписок нет.
3. **Пока не вызван `BX24.installFinish()`, приложение считается неустановленным:** виджеты
   не показываются, события не приходят вообще. Мастер установки обязан быть идемпотентным.

Алерт «ноль событий за 24 часа при наличии изменений в кэше» — единственный способ заметить,
что нас тихо отключили.

## 6. Исходящая очередь

`outbox` с приоритетами: интерактивные ответы > уведомления > отчёты.
Лимитер на чат (`tg_chat_budget`): 20 сообщений в минуту на группу — потолок Telegram.
Пять неудачных попыток → `failed`, алерт админу теннанта.

**Группировка уведомлений (реализована 25.08.2026, миграция `0016`).** Чат — или проект,
или теннант — может попросить присылать новости не по одной, а сводкой раз в N минут
(настройка в приложении Б24, docs/50-web-and-b24-app.md §2.9; хранение и цепочка
наследования — docs/20-data-model.md §9). Механика:

* при постановке в очередь строка помечается `digest=true`, а её `next_attempt_at` —
  это время отправки сводки: `now() + интервал` либо уже открытое окно этого чата;
* обычная отправка такие строки не видит (`WHERE NOT o.digest`) — иначе группировка
  была бы включена на вид и не делала бы ничего;
* `worker.flush_digests()` собирает закрывшиеся окна по ключу «чат + тема форума».
  Окно с одной новостью уходит обычным уведомлением со своими кнопками; окно из
  нескольких — сводкой без кнопок (двадцать наборов кнопок не относятся к сообщению
  целиком, а номер задачи в каждой строке остаётся ссылкой на портал);
* не влезло в одно сообщение — уходит следующим, с указанием «строки 26–50 из 74».
  Молчаливое усечение здесь запрещено дважды: общим правилом проекта и смыслом самой
  сводки — она существует, чтобы новость не пропала.

Схлопывание нескольких изменений ОДНОЙ задачи в одно сообщение — по-прежнему замысел, а не
код: группировка работает по чату, а не по задаче.

При `migrate_to_chat_id` все `pending` записи переадресуются на новый `chat_ref`, иначе они
упрутся в `400` и уйдут в мёртвые.

## 7. Веб-панель, приложение в Б24, Traefik

| Маршрут | Куда | Примечание |
|---|---|---|
| `/` | статика панели (React, собранная в CI) | отдаёт `b24bot-api` |
| `/api/v1/*` | FastAPI | сессия в httpOnly-куке |
| `/app/*` | страницы placement внутри Б24 | `frame-ancestors` динамический |
| `/b24/install`, `/b24/events`, `/b24/placement` | обработчики приложения | IP-allowlist Битрикса |
| `/tg/{webhook_id}` | приём апдейтов | IP-allowlist Telegram |
| `/miniapp/*` | мини-апп Telegram (React, собран в образе) | `frame-ancestors` под клиенты Telegram |
| `/api/miniapp/*` | API мини-аппа | `Authorization: tma <initData>` на каждом запросе |

**Мини-апп живёт по пути, а не на поддомене.** Отдельный хост потребовал бы своей A-записи,
своего сертификата и своей строки в Traefik — при нулевой выгоде: страница и API уже на
одном домене, CORS не нужен, кука не используется вовсе.

Оба маршрута мини-аппа идут через тот же роутер Traefik, что и страницы Битрикса, —
**без `security-headers@file`**: в нём `frameDeny: true`, а Telegram Desktop и веб-клиент
открывают мини-апп в iframe. `X-Frame-Options: DENY` дал бы там пустое окно без единого
сообщения об ошибке. Заголовки для `/miniapp` выставляет само приложение (`api/main.py`):
CSP с поимённым списком доменов Telegram, `nosniff`, `noindex`.

Туда же добавлен `/b24/app` — экран настроек приложения тоже открывается в iframe портала,
а под прежнее правило `/app` он не подпадал.

`frame-ancestors` выдаётся **динамически под домен проверенного портала**, а не общим
`*.bitrix24.ru`: иначе страницу встраивает любой бесплатный портал, созданный за пять минут.
BX24 SDK самохостим или подключаем с SRI. Сессионный токен во фрагменте URL очищается сразу
после чтения.

Логи Traefik: для `/b24/*` и `/tg/*` **query-строка не пишется** — в OAuth-колбэке едут `code`
и `member_id`, а access-лог лежит на общей машине.

**`llm/` появляется в фазе 1, хотя LLM не используется.** `NullProvider` всегда возвращает

переписан — что и требовалось не допустить.

## 9. Тестирование

Критерий приёмки — «все тесты зелёные». При отсутствии человеческого ревью тесты и есть
второй инженер, поэтому список обязательный:

- **Юниты**: извлечение заголовка и описания, парсер дат, экранирование, маппинг полей
  Битрикса (UPPER на вход / camelCase на выход), разрешение настроек с наследованием.
- **Интеграционные с настоящим PostgreSQL** (testcontainers): репозитории, RLS, миграции
  вперёд и назад, очередь.
- **`FakePortal`** — контрактный дубль Битрикса на сырых payload, снятых спайками. Все ответы
  и ошибки (`QUERY_LIMIT_EXCEEDED`, `OPERATION_TIME_LIMIT`, `invalid_grant`) воспроизводимы.
- **Мок Telegram** — проверка исходящих вызовов и лимитеров.
- **Тесты изоляции**: два теннанта с одинаковыми данными, ни один запрос не видит чужое;
  чат клиента A не открывает задачу клиента B.
- **Тесты безопасности**: инъекции HTML и BBCode через имена, названия чатов и имена файлов;
  bidi-символы; перебор номеров задач; подделка события; гонка обновления токена с отменой
  задачи на середине (ноль зависших локов, ноль `invalid_grant`).
- **Канареечный тест И-1**: текст сообщения не находится ни в одной таблице.

## 10. Деплой на боевой сервер

Отдельной среды нет — решение заказчика. Значит скрипт деплоя обязан быть параноидальным.

Реализовано 17.08.2026: мердж в `main` → `.github/workflows/deploy.yml` → проверки
(`ci.yml`) → сборка образа в GitHub Actions и публикация в GHCR → `scripts/deploy.sh`
по ssh. На сервере не собирается ничего, туда едут только `docker-compose.yml`, скрипты
и тег образа. Пошаговый разбор и список секретов — [80-deploy.md](80-deploy.md) §8.

```
1. flock: одна выкатка за раз (две сессии уже затирали друг друга)
2. проверка свободного места (отказ при занятости >85%)
3. .env на месте и без значений в кавычках (docker --env-file их не снимает)
4. docker pull тега сборки (образы собраны в CI, на сервере ничего не собирается)
5. дамп БД в backups/ + проверка хвоста на «dump complete», а не только размера
6. alembic upgrade head одноразовым контейнером НОВОГО образа, до подъёма сервисов
7. docker compose up -d --no-build
8. сверка digest каждого контейнера с digest выкаченного образа
9. health-check всех четырёх контейнеров + curl /health снаружи
10. при провале — автоматический откат образа; docker builder/image prune until=168h
```

Шаг 8 — не формальность: 16.08 все контейнеры были `healthy` со старым кодом внутри,
и ни одна проверка состояния этого не показала.

Откат: `scripts/rollback.sh` — предыдущий тег образа, при желании `alembic downgrade`
и восстановление дампа. Одной командой. Автоматика откатывает **только образ**:
схема вперёд-совместима и старый код с ней работает, а автоматический `DROP DATABASE`
на боевых данных пилота — худшее, что можно сделать в момент уже случившейся аварии.

Миграции пишутся так, чтобы старый и новый код переживали друг друга: сначала добавляем
колонку, потом заполняем, потом начинаем читать, и только следующим релизом убираем старое.

Пока идёт разработка — один теннант (DEVON), один тестовый чат, feature-флаги на уровне
теннанта. Боевые чаты «Линии Жизни» подключаются после приёмочных сценариев.

## 11. Наблюдаемость

- Структурные логи JSON, обязательные поля `tenant_id`, `trace_id`. **Скраббер** телефонов,
  почты и токенов перед записью; регулярка телефонов — по цифрам с разделителями
  (`(?:\+?\d[\s\-()]*){10,15}`), иначе `8 999 123-45-67` проходит мимо.
- `/health`: БД, глубина очередей, свежесть синхронизации, состояние вебхуков, свободный диск.
- **Пульс процессов без порта.** У `bot` и `worker` HTTP-сервера нет, поэтому healthcheck
  у них не curl: цикл на каждом успешном обороте зовёт `heartbeat.beat(<имя>)`, а
  healthcheck запускает `python -m b24bot.core.heartbeat <имя> <предел>` и валится, если
  метка устарела или её нет вовсе. Пределы: бот 180 с, воркер 120 с. Пульс бота ставит
  супервизор, а не поллер — поллер законно висит в `getUpdates` до 25 секунд.
  Файл на каждый процесс свой: образ один, контейнера три. Историю обеих ошибок,
  из-за которых это появилось, см. docs/80-deploy.md.
- Метрики в формате Prometheus — подключение к стандартному стеку компании отложено, но
  точки съёма делаются сразу.
- Алерты, которые нельзя откладывать: ноль событий за 24 часа, рост `needs_reauth`,
  мёртвые записи в очереди, диск >80%, аномальная доля подавленных эхо-уведомлений.

**Аварийный канал.** Все алерты админу теннанта идут в личку его же бота — но самая
вероятная авария и есть смерть этого бота. Поэтому админ теннанта при онбординге обязан
один раз нажать `/start` у бота DEVON, и алерты уровня «бот теннанта нерабочий»,
«приложение удалено с портала», «сервисный токен мёртв» уходят туда.

## 12. Смена домена

К `PUBLIC_BASE_URL` привязаны `placement.bind`, `event.bind` и `setWebhook`. Битрикс ключует
встройку по URL обработчика и сам ничего не удаляет. Процедура переезда: перерегистрировать
placement, пересоздать подписки, переустановить вебхуки всех ботов, удалить старые встройки
вручную. Без неё теннант остаётся с мёртвыми вкладками и потерянными подписками.
