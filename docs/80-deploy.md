(см. [70-plan.md](70-plan.md) §3).

Разные заголовки на разных путях — это и есть смысл двух роутеров: страницу приложения
портал сможет открыть в iframe, а всё остальное защищено обычным `frameDeny`.
`frame-ancestors` выдаётся под домен **конкретного проверенного портала**, а не общим
`*.bitrix24.ru`. Placement с недоверенным доменом отклоняется (инвариант И-4).

**Что осталось:** зарегистрировать приложение на портале (§3) и установить его (§4).

### Две ошибки, найденные при первом развёртывании

1. **`postgres` требует `-c` и значение разными аргументами.** Форма `-c=key=value` даёт
   `FATAL: unrecognized configuration parameter ""`, контейнер уходит в цикл перезапусков,
   а кластер остаётся **недоинициализированным**: база не создана и в `pg_hba.conf` нет
   строки `host all all all scram-sha-256`. Лечится только пересозданием тома.
2. **`pg_isready` не годится как healthcheck.** На сломанном кластере он рапортовал `healthy`,
   потому что проверяет лишь то, что сервер отвечает. Заменён на реальный
   `psql -c 'SELECT 1'` к нашей базе.

### Третья ошибка, найденная 16.08 вечером: healthcheck без проверки

`bot` и `worker` не слушают порт. `worker` наследовал `HEALTHCHECK` из образа —
`curl -fsS http://localhost:8000/health` — и потому числился `unhealthy` **103 проверки
подряд**, работая при этом нормально. У `bot` в compose стояла заглушка
`python -c "import sys; sys.exit(0)"`, которая проходила всегда, то есть тоже не
проверяла ничего. Два противоположных дефекта с одним следствием: статус контейнера
не сообщает о его состоянии.

Заменено на пульс (`core/heartbeat.py`): цикл на каждом успешном обороте пишет метку
времени в файл, healthcheck смотрит на её свежесть.

```yaml
test: ["CMD", "python", "-m", "b24bot.core.heartbeat", "worker", "120"]
```

Пульс бота ставит **супервизор** (`PollerRegistry.run_forever`, оборот раз в 30 с),
а не сам поллер: поллер законно висит в `getUpdates` до 25 секунд, и его молчание —
норма, а не сбой. Предел бота 180 с, воркера — 120 с.

Файл пульса свой на каждый процесс: образ один, контейнера три, и общий файл означал бы,
что живой бот «лечит» мёртвого воркера. Ошибка записи пульса проглатывается — диагностика
не имеет права уронить рабочий цикл.

Traefik выпускает сертификат по HTTP-01 challenge, и без корректной A-записи выпуск не пройдёт.

**Сеть Traefik.** Уже существует, называется `traefik-public`, наш compose подключается к ней
как к внешней. Ничего создавать не надо.

**Место.** Освободить мусор Docker до первой сборки — на машине ~41 ГБ реклейма:

```bash
docker builder prune -af && docker image prune
```

> `docker volume prune` и `docker system prune --volumes` **не запускать никогда**:
> на машине 61 неактивный volume, принадлежащий чужим остановленным контейнерам.

## 2. Развёртывание

```bash
git clone <repo> /opt/b24sdbot && cd /opt/b24sdbot
cp .env.example .env && chmod 600 .env
```

Заполнить `.env`. Мастер-ключ сгенерировать так:

```bash
python3 -c "import os,base64;print(base64.urlsafe_b64encode(os.urandom(32)).decode().rstrip('='))"
```

`POSTGRES_PASSWORD` — длинный случайный, он же подставляется в `DATABASE_URL`.

Сборка образа делается **отдельно и в одиночку**: рядом работает чужой прод без лимитов
памяти, параллельная сборка — реальный шанс уронить его по OOM.

```bash
cd /opt/b24sdbot && docker compose build
```

```bash
cd /opt/b24sdbot && docker compose up -d
```

Миграции:

```bash
cd /opt/b24sdbot && docker compose run --rm -T --no-deps api alembic upgrade head
```

**Именно `run`, а не `exec`.** `exec` заходит в РАБОТАЮЩИЙ контейнер, а он поднят со старого
образа: alembic видит там старый каталог миграций, отвечает «уже head» и молча ничего не
делает — проверено 18.08.2026 на миграциях `0013` и `0014`. `run` создаёт контейнер из
свежесобранного образа, поэтому видит новые ревизии. Порядок: собрать образ → накатить
миграции этой командой → пересоздать сервисы. Тогда новый код не стартует на старой схеме
даже на секунду.

Проверка:

```bash
curl -fsS https://b24sdbot.devondev.ru/health
```

Ожидаем `{"status":"ok","checks":{"db":"ok"}}`. Если TLS не поднялся — смотреть
`docker logs traefik` на предмет ошибки ACME.

## 4. Установка и что должно произойти

Нажать «Установить». Ожидаемое поведение:

1. Битрикс POST-ит на `/b24/install` токены установщика.
2. Мы создаём теннанта, сохраняем `APPLICATION_TOKEN` и токены установщика как

3. Страница вызывает `BX24.installFinish()`, и приложение появляется в левом меню.

```bash
cd /opt/b24sdbot && docker compose exec -T postgres psql -U b24sdbot -d b24sdbot -c "SELECT id, b24_domain, install_state, array_length(granted_scope,1) AS scopes FROM tenants"
```

## 5. SPIKE A: что снимаем

Скелет пишет структуру каждого входящего payload в `b24_payload_log` — **значения секретов
маскируются до записи**, сохраняются только имена полей и несекретные значения. Это и есть
цель спайка: узнать, что реально присылает портал.

```bash
cd /opt/b24sdbot && docker compose exec -T postgres psql -U b24sdbot -d b24sdbot -c "SELECT kind, received_at, jsonb_pretty(shape) FROM b24_payload_log ORDER BY id DESC LIMIT 5"
```

Чек-лист спайка:

1. **Установка от администратора** — пришли ли `AUTH_ID`, `REFRESH_ID`, `APPLICATION_TOKEN`,
   `member_id`, какой набор полей на самом деле.
2. **Открыть приложение от НЕ-администратора** — приходит ли placement-POST с его `AUTH_ID`,
   совпадает ли `APPLICATION_TOKEN` с полученным при установке.
3. **Появился ли per-user токен второго человека:**

   ```bash
   cd /opt/b24sdbot && docker compose exec -T postgres psql -U b24sdbot -d b24sdbot -c "SELECT tenant_id, b24_user_id, role, state, expires_at FROM b24_user_tokens"
   ```

4. **Открывается ли страница в iframe.** Если браузер ругается на `X-Frame-Options` — значит
   маршрут ушёл не на тот роутер Traefik. В `docker-compose.yml` для `/b24/placement` и `/app`
   намеренно **не** подключён `security-headers@file`: в нём `frameDeny: true`, и портал
   не смог бы встроить страницу. `frame-ancestors` выставляет само приложение, динамически
   под домен проверенного портала.
5. **Доживает ли кука `SameSite=None`** до второго запроса внутри iframe.
6. **`/oauth/authorize/` с `response_type=code` и `redirect_uri`** — работает ли собственный
   редирект для локального приложения (в документации Битрикса не описан).

По итогам спайка дописать факты в [00-portal-facts.md](00-portal-facts.md) и только потом
писать полную схему БД.

## 6.1 Мини-апп: что нужно при выкатке

Ручных шагов нет. Всё, что требуется, делает сборка и само приложение:

1. **Образ.** Фронтенд собирается первым этапом `Dockerfile` (`node:22-alpine` →
   `npm ci` → `vite build`) и попадает в питоновский образ статикой в `/app/web/miniapp`.
   Несобирающийся TypeScript валит сборку образа — и это правильное место для отказа,
   потому что внутри Telegram консоль браузера не открыть.
2. **Миграция `0010`** добавляет `tg_bots.miniapp_short_name`. Дамп перед накатом
   обязателен, как и для любой другой.
3. **Traefik** уже настроен: `/miniapp` и `/api/miniapp` идут по маршруту без
   `frameDeny` (см. [10-architecture.md](10-architecture.md) §7). Отдельного домена
   и отдельной A-записи не нужно.
4. **Кнопка меню бота** ставится автоматически при подключении бота и при каждой
   проверке связи на экране приложения в Битрикс24.

Проверка после выкатки:

```bash
cd /opt/b24sdbot && curl -sS https://b24sdbot.devondev.ru/health && curl -sSI https://b24sdbot.devondev.ru/miniapp | head -20
```

Ожидаем `"miniapp":"ok"` в health и заголовок `Content-Security-Policy: … frame-ancestors
https://web.telegram.org …` у страницы. `X-Frame-Options` в ответе быть **не должно**:
он означает, что маршрут ушёл на роутер с `security-headers@file`, и в Telegram Desktop
приложение откроется пустым окном.

Необязательный шаг для теннанта: `/newapp` в BotFather, адрес
`https://b24sdbot.devondev.ru/miniapp`, короткое имя ввести на экране приложения в
Битрикс24. Тогда из группового чата мини-апп открывается в одно касание вместо двух.

## 8. CI/CD

Правило проекта — образы собираются в CI, на сервере не собирается ничего
([10-architecture.md](10-architecture.md) §10). До 17.08.2026 оно нарушалось: образ
собирался на сервере из дерева, доставленного tar-ом, и это дало две аварии подряд
(молча не обновлённые файлы; две сессии, затирающие друг друга). Теперь на сервер
едут только `docker-compose.yml`, два скрипта и **тег образа**.

### 8.1 Что происходит при мердже в `main`

`.github/workflows/deploy.yml`, три job-а подряд:

| Job | Что делает | Чем останавливает плохое |
|---|---|---|
| `checks` | вызывает `ci.yml` целиком | красный ruff / mypy / pytest / gitleaks / сборка образа = выкатки не будет |
| `build` | buildx → GHCR, теги `sha-<12>` и `latest` | несобираемый образ дальше не проходит |
| `deploy` | scp compose и скриптов, `scripts/deploy.sh` по ssh | см. 8.3 |

`ci.yml` живёт отдельно и запускается сам на каждом pull request. Пять проверок:
`ruff check` · `mypy --strict` · `pytest` на **настоящей PostgreSQL 16** (без неё тесты
изоляции и миграций пропускают сами себя — отдельный шаг падает, если они пропущены) ·
`npm run build` мини-аппа (`tsc --noEmit && vite build`) · `gitleaks` по всей истории
(инвариант И-7, конфиг `.gitleaks.toml`).

Очередь выкаток — `concurrency: production-deploy` с `cancel-in-progress: false`.
Отменять начатую выкатку опаснее, чем подождать; на сервере тот же запрет продублирован
через `flock` на `.deploy.lock`, потому что руками скрипт тоже можно запустить.

### 8.2 Секреты и переменные репозитория

Settings → Secrets and variables → Actions:

| Имя | Тип | Значение |
|---|---|---|
| `DEPLOY_HOST` | secret | `91.142.94.189` |
| `DEPLOY_USER` | secret | `root` |
| `DEPLOY_SSH_KEY` | secret | приватный ключ целиком, включая строки `-----BEGIN/END-----` |
| `DEPLOY_KNOWN_HOSTS` | secret | строка `91.142.94.189 ssh-ed25519 AAAA…`, см. ниже |
| `DEPLOY_DIR` | variable | необязательно, по умолчанию `/opt/b24sdbot` |

`DEPLOY_KNOWN_HOSTS` обязателен: `StrictHostKeyChecking=no` в пайплайне, который держит
ssh-ключ от root боевого сервера, — это подпись под любым MITM в сети раннера.

Взять значение проще всего из своего же `known_hosts` — там лежит ключ, которому
машина доверяет с прошлых деплоев:

```bash
ssh-keygen -F 91.142.94.189 | grep -v '^#'
```

**`ssh-keyscan` из комплекта Windows на этом сервере не работает:** падает с
`choose_kex: unsupported KEX method sntrup761x25519-sha512@openssh.com`. Клиент
`C:\Windows\System32\OpenSSH\` старше сервера и не знает постквантовый KEX, который
тот предлагает первым. Сервер тут ни при чём, обычный `ssh` ходит нормально. Если
ключ нужен именно с сервера, а не из `known_hosts` — брать `ssh-keyscan` из Git Bash
(`/usr/bin/ssh-keyscan`), он свежее.

`ssh-rsa` в секрет не класть: ключ на сервере рабочий, но выбирать подпись на SHA-1
там, где есть ed25519, незачем.

Токен GHCR отдельным секретом **не нужен**: публикует образ `GITHUB_TOKEN` самого прогона,
он же уходит на сервер для `docker login` — через stdin, а не аргументом команды
(аргументы видны в `ps` всей машине, а машина общая с чужим продом). Скрипт делает
`docker logout` за собой. Токен живёт до конца job-а, поэтому вручную скачать образ
с сервера позже им не выйдет — для этого нужен PAT с `read:packages`.

Гейт на человека, если понадобится: Settings → Environments → `production` →
Required reviewers. Кода это не касается, job `deploy` уже привязан к этому environment.

### 8.3 Что делает `scripts/deploy.sh` на сервере

Порядок из [10-architecture.md](10-architecture.md) §10, каждый шаг — след отдельной аварии:

1. `flock` — одна выкатка за раз.
2. Свободное место: отказ, если занято больше 85%.
3. `.env` на месте и **без значений в кавычках** — `docker run --env-file` кавычки
   не снимает, а compose снимает; в кавычках `DATABASE_URL` молча стал бы неверным.
4. `docker pull` тега этой сборки.
5. Запоминается образ работающего контейнера — это и есть точка отката.
6. **Дамп базы** в `backups/`, с проверкой хвоста на `PostgreSQL database dump complete`:
   оборванный дамп выглядит как нормальный файл.
7. `alembic upgrade head` **одноразовым контейнером нового образа, до подъёма сервисов**.
   Порядок именно такой: миграции вперёд-совместимы (старый код переживает новую схему),
   обратное не гарантировано.
8. `APP_IMAGE` пишется в `.env`, `docker compose up -d --no-build api bot worker`.
9. **Digest каждого запущенного контейнера сверяется с digest-ом выкаченного образа.**
   Прямая защита от аварии 16.08, когда все контейнеры были `healthy` со старым кодом.
10. Ожидание `healthy` у всех четырёх контейнеров + `curl /health` снаружи.
11. `docker builder prune` и `docker image prune` с `until=168h`. **Без `-a`**: с ним
    prune снёс бы неиспользуемые образы соседей по машине.

При провале любого шага после подъёма — автоматический откат **образа** на предыдущий.
База при этом не откатывается сознательно: схема вперёд-совместима, старый код с ней
работает, а автоматический `DROP DATABASE` на боевых данных пилота — худшее, что может
сделать скрипт в момент, когда что-то уже пошло не так. В логе и в summary прогона
печатается путь к дампу и ревизия до миграции.

### 8.4 Откат руками

```bash
cd /opt/b24sdbot && ./scripts/rollback.sh
```

Без аргументов — предыдущий образ из `.deploy/history`. Дальше по нарастающей:

```bash
cd /opt/b24sdbot && ./scripts/rollback.sh --to ghcr.io/devondevceo/devon_b24_support_bot:sha-abc123def456 --migrations -1
```

```bash
cd /opt/b24sdbot && ./scripts/rollback.sh --with-db backups/pre-deploy-20260817-120000.sql.gz
```

`--with-db` пересоздаёт базу и спрашивает подтверждение (`--yes` отключает вопрос).
Перед любым откатом скрипт **сам снимает дамп** текущего состояния: состояние «после
аварии» — тоже данные, и восстановить его иначе будет неоткуда.

### 8.5 Аварийная сборка, если GitHub недоступен

```bash
cd /opt/b24sdbot && docker build -t "$(grep ^APP_IMAGE= .env | cut -d= -f2-)" . && docker compose up -d --no-build api bot worker
```

Дерево на сервере при этом обязано соответствовать `main`, а это ровно то допущение,
которое дважды оказывалось ложным. Проверять контрольные суммы (CLAUDE.md, «Где что лежит»).

### 8.5 Если выкатка падает на «Permission denied (publickey)»

Так выглядит ключ, которого нет в `~/.ssh/authorized_keys` на сервере. Больше ничего
увидеть не получится: **sshd на `LogLevel INFO` отвергнутые ключи в журнал не пишет
вовсе** — проверено 18.08.2026 пробным ключом, в `journalctl -u ssh` от такой попытки
остаётся только `Connection closed by authenticating user root <ip> [preauth]`, без
отпечатка и без слова `publickey`.

Поэтому `deploy.yml` печатает отпечаток ключа выкатки в лог шага, а при отказе кладёт
в summary прогона готовую строку для `authorized_keys`. Публичный ключ секретом
не является — установить надо ровно его.

Сверить, что ключ на месте:

```bash
ssh-keygen -lf ~/.ssh/authorized_keys
```

Отпечаток из лога прогона обязан быть в этом списке. Если его там нет — либо добавьте
строку из summary, либо положите в секрет `DEPLOY_SSH_KEY` тот ключ, который уже разрешён.

**Пока ключ не установлен, выкатка руками идёт аварийным путём** (он же описан
комментарием в `docker-compose.yml`): образ собирается на сервере с тем же тегом,
что дал бы CI, и дальше обычные шаги — дамп, миграции из нового образа, `up -d`.

```bash
IMAGE=ghcr.io/devondevceo/devon_b24_support_bot:sha-$(git rev-parse HEAD | cut -c1-12)
docker build -t "$IMAGE" . && sed -i "/^APP_IMAGE=/d" .env && echo "APP_IMAGE=$IMAGE" >> .env
docker run --rm --network b24sdbot-internal --env-file .env "$IMAGE" alembic upgrade head
docker compose up -d --no-build api bot worker
```

### 8.6 Проверка дампа: маркер завершения больше не последняя строка

`pg_dump` 16.13 дописывает **после** `-- PostgreSQL database dump complete` строку
`\unrestrict <токен>` — это защита от подмены команд при восстановлении, добавленная
патчами 2025 года. Маркер оказывается пятой строкой с конца, а не первой.

Проверка целостности дампа в `scripts/deploy.sh` и `scripts/rollback.sh` смотрела три
последние строки и потому объявила **целый** дамп оборванным, уронив первую же успешную
выкатку (19.08.2026). Хвост увеличен до 20 строк.

Проверять надо именно маркер, а не размер файла и не `gzip -t`: оборванный на середине
дамп — это валидный gzip приличного размера, в котором просто нет половины данных.

### 8.7 «Контейнер healthy» и «Traefik уже переключился» — разные события

Выкатка 19.08.2026 дошла до конца, дождалась четырёх `healthy` контейнеров — и упала
на публичном `/health`, откатив совершенно рабочий релиз. Проверка навредила ровно там,
где должна была защитить.

Причина: Traefik узнаёт о пересозданном контейнере по событию Docker, с задержкой
в секунду-другую. Внутренний healthcheck к этому моменту уже зелёный — он ходит внутрь
контейнера, минуя маршрутизацию. Одиночный `curl` попадает в этот зазор.

Публичная проверка в `deploy.sh` и `rollback.sh` теперь идёт с повтором до
`PUBLIC_TIMEOUT` (90 секунд по умолчанию). Сама проверка остаётся обязательной:
она единственная отвечает на вопрос «а снаружи-то работает», на который внутренние
healthcheck-и не отвечают в принципе.
