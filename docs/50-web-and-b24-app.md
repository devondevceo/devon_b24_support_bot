# Веб-панель, приложение внутри Битрикс24 и мини-апп

Интерфейсы к одним и тем же операциям. **Набор операций один**, и он обязан совпадать
с админ-командами бота из [30-bot-spec.md](30-bot-spec.md) §9 — иначе интерфейсы разъедутся
и начнут делать разное.

Разделение обязанностей:

| Где | Что делается | Почему именно там |
|---|---|---|
| **Приложение в Б24** | привязка сотрудника, привязка проекта к чату из карточки проекта, статус интеграции | там уже есть контекст (кто ты, какая группа) и там сидят сотрудники теннанта |
| **Веб-панель** | всё управление: теннанты, клиенты, проекты, привязки, дефолты, уведомления, пользователи, аудит | нужны таблицы, фильтры и второй фактор |
| **Бот** | быстрые операции в контексте чата: `/bind`, `/notify`, `/health` | рука уже в чате |
| **Мини-апп** | работа с задачами: списки с фильтрами, карточка, срок, ответственный, приоритет, комментарии, создание задачи полной формой | форма там, где в чате были бы двадцать кнопок; см. часть 3 |

# Часть 1. Веб-панель

Стек: React + Vite, собирается в CI, на сервер приезжает готовый `dist`, отдаётся FastAPI
за Traefik. Язык — русский.

## 1.1 Аутентификация

Два входа, оба ведут к одной сессии:

**Telegram Login Widget.** При модели «свой бот у каждого теннанта» виджет нельзя привязать
к боту теннанта: `client_id` виджета — это конкретный бот, а `redirect_uri` регистрируется
в BotFather его владельцем, то есть теннантом. Решение: **вход через единый бот DEVON**
(`@devon_support_login_bot`), домен зарегистрирован нами один раз. Бот теннанта для входа
не используется вообще. Он же служит аварийным каналом уведомлений.

**Логин и пароль.** Argon2id, блокировка после серии неудач. Нужен, когда Telegram недоступен.

**TOTP обязателен для `tenant_admin` и `devon_superadmin`** (обоснование — [40-security.md](40-security.md) §13).

**Сессия** — httpOnly-кука, срок 12 часов, `web_sessions` с полем `session_epoch`. Роль
читается из БД на каждом запросе; при смене роли или пароля `users.session_epoch`
инкрементируется и все сессии умирают.

### Жизненный цикл учётной записи

SMTP в проекте нет и не планируется, поэтому доставка — через бота DEVON в личку:

1. Суперадмин создаёт админа теннанта, указывая его `tg_user_id` (или приглашая по
   одноразовой ссылке).
2. Приглашённый получает в личке бота DEVON ссылку с одноразовым токеном, TTL 30 минут.
3. Первый вход — принудительная установка пароля и подключение TOTP.
4. Сброс пароля — тем же каналом. Кода в чат не пишем, только ссылку.
5. При отзыве доступа — `session_epoch++`, все сессии мгновенно недействительны.

**Бутстрап первого суперадмина.** При пустой таблице `users` стартовый хук создаёт
суперадмина из `SUPERADMIN_TG_USER_ID` в окружении и печатает в лог одноразовый код привязки.
После первого успешного входа переменная окружения игнорируется навсегда.

## 1.2 Карта экранов

```
Вход
└── Дашборд
    ├── Теннанты (только суперадмин)
    │   └── Карточка теннанта
    │       ├── Портал Битрикс24
    │       ├── Telegram-бот
    │       ├── Клиенты
    │       │   └── Карточка клиента → Проекты
    │       ├── Проекты
    │       │   └── Карточка проекта → Привязки, Дефолты полей
    │       ├── Привязки чат ↔ проект
    │       ├── Уведомления
    │       ├── Пользователи и сопоставления
    │       ├── Аудит
    │       └── Здоровье интеграции
    └── Профиль (пароль, TOTP, сессии)
```

Админ теннанта попадает сразу в карточку своего теннанта, раздел «Теннанты» ему не виден.

Каждый экран обязан иметь четыре состояния: **загрузка**, **пусто** (с объяснением, что
сделать), **ошибка** (с кодом и кнопкой «повторить»), **нет прав** (без раскрытия
существования объекта).

## 1.3 Экраны

**Дашборд.** Плитки: активных чатов, привязанных проектов, задач создано за неделю,
непривязанных сотрудников, состояние интеграции (зелёный/жёлтый/красный), очередь.
Для суперадмина — то же в разрезе теннантов.

**Теннанты** (суперадмин). Таблица: название, портал, бот, клиентов, чатов, статус,
последняя активность. Действия: создать, приостановить, удалить (с подтверждением вводом
названия — процедура удаления в [40-security.md](40-security.md) §14).

**Портал Битрикс24.** Показывает: домен, `member_id`, состояние установки приложения,
выданные scope, срок жизни токена установщика, сервисные учётки (`service_admin`,
`service_reader`) с состоянием. Действия: «Установить приложение» (даёт ссылку и инструкцию),
«Переустановить», «Назначить сервисного читателя», «Проверить подключение» (живой вызов
`app.info` с показом результата).

**Telegram-бот.** Поле ввода токена — **единственное место в системе, где токен вводится**
(в чат его писать запрещено). При сохранении: `getMe`, проверка занятости `bot_id`, установка
вебхука. Показывает: username, состояние вебхука («настроен» / «не настроен» — **без вывода
URL**), режим (webhook/polling), последняя проверка. Действия: «Перевыпустить вебхук»,
«Проверить», «Отключить».

**Клиенты.** Таблица: название, компания в CRM, проектов, чатов, статус. Создание: название
плюс выбор компании из CRM через поиск по `crm.company.list` (на портале их 2094, поэтому
именно поиск, а не выпадающий список). Связь используется в карточке задачи, в сводках
и во вкладке компании в CRM — если бы не использовалась, поле и вкладку следовало бы убрать.

**Проекты.** Кнопка «Импортировать из Битрикс24» тянет `sonet_group.get` и показывает группы
чекбоксами с уже импортированными в неактивном состоянии. Таблица: название, ID группы,
клиент, тип, экстранет, чатов, задач в кэше, состояние синхронизации.

**Карточка проекта.** Стадии канбана (только чтение, синхронизируются из Б24), дефолты полей
задачи, привязанные чаты, кнопка «Синхронизировать сейчас».

**Привязки.** Таблица: чат, топик, проект, клиент, кто привязал, когда, состояние.
Чат выбирается **только из списка тех, где бот реально присутствует** — ручной ввод `chat_id`
запрещён (обоснование — [40-security.md](40-security.md) §4). Проверка «все проекты чата
принадлежат одному клиенту» выполняется до сохранения с внятным сообщением.

**Дефолты полей задачи.** Форма на уровне теннанта и на уровне проекта: ответственный,
приоритет, срок «+N дней», наблюдатели, соисполнители, стадия. У каждого поля три состояния:
**наследовать**, **задать значение**, **сбросить**. UI обязан писать явный `false`/`null`,
а не удалять запись (инвариант И-9).

**Уведомления.** Матрица «код события × уровень (теннант / проект / привязка)» с тремя
состояниями в каждой ячейке: наследовать, включено, выключено. Отдельно видно, откуда
унаследовано текущее значение.

**Пользователи и сопоставления.** Таблица: имя в Telegram, `tg_user_id`, пользователь Б24,
статус (`none` / `matched` / `authorized` / `needs_reauth`), когда привязан, последняя
активность. Действия: пригласить (ссылка в личку), сопоставить вручную (**даёт только
`matched`**), снять сопоставление, отправить напоминание о переавторизации.
Отдельный счётчик «сколько сотрудников не привязано» — это метрика онбординга, а не дефект.

**Аудит.** Фильтры: период, пользователь, действие, клиент, проект, только высокорисковые.
Экспорт в CSV с экранированием формул. Режим аудита переключается здесь же, с явным
предупреждением, что `minimal` вступит в силу через 24 часа.

**Здоровье интеграции.** Состояние портала, вебхуков, подписок на события, очередей,
свежести кэша, свободного диска. Кнопки: «Проверить всё», «Пересоздать подписки»,
«Принудительная синхронизация». Здесь же — предупреждения вида «событий не приходило 24 часа».

## 1.4 Контракт API

Все ответы — JSON. Ошибка: `{"error": {"code": "...", "message": "...", "details": {...}}}`.
Коды: `400 validation`, `401 unauthenticated`, `403 forbidden`, `404 not_found`,
`409 conflict`, `429 rate_limited`, `502 upstream_error` (Битрикс или Telegram).
Списки: `?page=1&per_page=50&q=&sort=`, ответ `{"items": [...], "total": N, "page": 1}`.

| Метод и путь | Роль | Что делает |
|---|---|---|
| `POST /api/v1/auth/telegram` | — | вход по подписи Login Widget |
| `POST /api/v1/auth/password` | — | вход по паролю |
| `POST /api/v1/auth/totp` | — | подтверждение второго фактора |
| `POST /api/v1/auth/logout` | любая | завершить сессию |
| `GET /api/v1/me` | любая | профиль, роль, теннант |
| `GET /api/v1/me/sessions` · `DELETE /api/v1/me/sessions/{id}` | любая | список и отзыв сессий |
| `GET /api/v1/tenants` · `POST` | superadmin | список, создание |
| `GET /api/v1/tenants/{id}` · `PATCH` · `DELETE` | superadmin | карточка, изменение, удаление |
| `GET /api/v1/tenants/{id}/portal` | admin | состояние портала |
| `POST /api/v1/tenants/{id}/portal/check` | admin | живой `app.info` |
| `POST /api/v1/tenants/{id}/portal/service-user` | admin | назначить `service_reader` |
| `GET /api/v1/tenants/{id}/bot` · `PUT` · `DELETE` | admin | бот теннанта, ввод токена |
| `POST /api/v1/tenants/{id}/bot/rewebhook` | admin | перевыпустить вебхук |
| `GET /api/v1/clients` · `POST` · `PATCH /{id}` · `DELETE /{id}` | admin | клиенты |
| `GET /api/v1/crm/companies?q=` | admin | поиск компании в CRM |
| `GET /api/v1/projects` · `PATCH /{id}` | admin | проекты |
| `POST /api/v1/projects/import` | admin | импорт групп из Б24 |
| `POST /api/v1/projects/{id}/sync` | admin | принудительная синхронизация |
| `GET /api/v1/projects/{id}/stages` | admin | стадии (только чтение) |
| `GET /api/v1/chats` | admin | чаты, где присутствует бот |
| `GET /api/v1/bindings` · `POST` · `DELETE /{id}` | admin | привязки |
| `GET /api/v1/defaults?scope=` · `PUT` | admin | дефолты полей задачи |
| `GET /api/v1/notifications?scope=` · `PUT` | admin | настройки уведомлений |
| `GET /api/v1/members` · `POST /{id}/map` · `DELETE /{id}/map` · `POST /{id}/invite` | admin | сопоставления |
| `GET /api/v1/audit` · `GET /api/v1/audit/export` | admin | аудит и экспорт |
| `PUT /api/v1/tenants/{id}/audit-mode` | admin | режим аудита |
| `GET /api/v1/health` | admin | здоровье интеграции |
| `POST /api/v1/health/resubscribe` | admin | пересоздать подписки |
| `GET /api/v1/queue` | superadmin | состояние очередей |

**IDOR.** Каждый обработчик резолвит объект **вместе с `tenant_id` из сессии** одним запросом,
а не «сначала достать, потом проверить». Отсутствие прав и отсутствие объекта дают одинаковый
`404`, кроме случаев, когда объект заведомо принадлежит запросившему.

# Часть 2. Приложение внутри Битрикс24

## 2.1 Установка

Тип — локальное серверное приложение, регистрирует администратор портала теннанта.

Мастер установки **обязан быть идемпотентным**: падение на середине не должно оставлять
теннанта в застрявшем состоянии, повторный запуск должен доводить установку до конца.

```
1. ONAPPINSTALL → сохранить member_id, домен, APPLICATION_TOKEN, токены установщика
                  как service_admin
2. placement.bind × 4 (см. 2.2)
3. event.bind на ONTASKADD, ONTASKUPDATE, ONTASKDELETE, ONTASKCOMMENTADD,
                ONAPPUPDATE, ONAPPUNINSTALL, ONAPPTEST
4. BX24.installFinish()   ← без него приложение считается неустановленным:
                            виджеты не показываются, события не приходят вообще
5. tenants.install_state = 'finished'
```

**`ONAPPUPDATE` перезаписывает `APPLICATION_TOKEN` и заново вызывает весь набор `event.bind`.**
Токен меняется при обновлении приложения, а обработчики событий при этом удаляются. Не сделать
этого — значит тихо перестать принимать события с полностью чистыми логами. Покрыто отдельным
тестом; плюс суточный `reconcile_events` сверяет подписки через `event.get` токеном
администратора и досоздаёт недостающие.

## 2.2 Точки встраивания

Регистрируем ровно четыре, и **у каждой есть содержимое**. Точку без содержимого не
регистрируем вовсе: пустая вкладка в карточке каждой задачи портала — это хуже, чем её
отсутствие.

### `LEFT_MENU` / `DEFAULT` — «Поддержка в Telegram»

> **Решение заказчика 16.08.2026: бот настраивается здесь, а не в веб-панели.**
> Токен Telegram-бота вводит администратор портала на этом экране. Реализовано в
> `src/b24bot/api/app_ui.py`. Что происходит при сохранении:
> `getMe` → проверка глобальной уникальности `bot_id` → шифрование и запись →
> `setWebhook` с секретом → косвенная проверка privacy mode по
> `can_read_all_group_messages`. Ни токен, ни URL вебхука обратно не показываются.
> Форма подписана короткоживущей сессией `app_sessions`, привязанной к
> `(теннант, пользователь Б24)`; права проверяются вызовом `user.admin` у самого портала.

Главный экран приложения. **Экрана два, и они разные** — это решение, а не деталь вёрстки.
Раньше страница была одна: пять карточек подряд, у сотрудника четыре из них read-only.

**Сотрудник** видит один вопрос и один ответ:

```
Ваш Telegram: @ivanov                   [привязан]
Вы можете создавать и комментировать задачи из привязанных чатов.

Ваши проекты в Telegram
  Поддержка сайта       — чат «Линия Жизни · поддержка» · клиент Линия Жизни
  Мобильное приложение  — чат «ЛЖ · мобилка» · клиент Линия Жизни
```

Если не привязан — на месте статуса крупная кнопка «Привязать Telegram» (см. 2.4),
рядом сам адрес ссылки: с десктопа человек пересылает его себе на телефон.
QR-кода нет — он потребовал бы внешнюю библиотеку, а внешних ресурсов на странице нет.

**Управляющий** (админ портала или `tenant_admin`) получает вкладки, а не простыню:

```
Обзор | Чаты 3 | Бот | Опросник | Подтверждение | Уведомления | Команда 3
```

| Вкладка | Что на ней |
|---|---|
| **Обзор** | одна строка состояния интеграции; пока настройка не закончена — мастер из трёх шагов, после — плитки охвата и данные портала |
| **Чаты** | чаты с ботом, привязки к проектам, форма привязки |
| **Бот** | токен, состояние, privacy mode, проверка подключения, замена бота, мини-апп |
| **Опросник** | наборы вопросов, порядок, привязка ответов к полям задачи (§2.7) |
| **Подтверждение** | подтверждение новой задачи ответственным (§2.8) |
| **Уведомления** | какие события доходят до чата и с какой группировкой (§2.9) |
| **Команда** | своя привязка Telegram и роли участников |

Пять решений, каждое из-за конкретной поломки:

1. **Состояние интеграции — одна строка, а не шесть полей на трёх карточках.**
   Порядок проверок в `app_ui._health` — это порядок, в котором всё ломается:
   нет бота → приостановлен → ошибка → **включён privacy mode** → нет чатов →
   нет привязок. Privacy mode стоит рядом с отказом Telegram намеренно: бот при нём
   формально «работает», но сообщений в группах не видит, то есть продукта нет.
2. **Активная вкладка ездит через скрытое поле `tab` в каждой форме.** Действия
   идут обычным POST с перерисовкой всей страницы; без этого поля «отвязать» в конце
   списка возвращало человека в начало «Обзора». Значение приходит от клиента и
   сверяется со списком (`safe_tab`).
3. **Мастер настройки вместо счётчиков на пустом теннанте.** До первой привязки все
   счётчики — нули, и смотреть на них незачем. Кнопка есть только у текущего шага:
   три кнопки разом — это три главных действия, то есть ни одного.
4. **Форма привязки свёрнута за `<details>`.** Раскрытая на каждом чате, она
   занимала больше места, чем сами чаты, и вкладка читалась как простыня из
   селектов (видно на скриншоте с прода 17.08). У чата без привязок форма
   раскрыта сразу: привязка и есть следующий шаг. JS не нужен, высоту iframe
   после раскрытия догоняет тот же `ResizeObserver`.
5. **Клиент выбирается только у чата без привязок.** Один чат обслуживает
   одного клиента, поэтому после первой привязки клиент фиксирован и назван
   текстом, а не селектом: выбор из списка был бы выбором между «правильно»
   и «ошибка сервера». Проверка на сервере при этом никуда не делась.

Вёрстка собирается компонентами из `src/b24bot/api/ui_kit.py` (токены, палитра
светлой и тёмной темы, иконки, компоненты). Внешних ресурсов нет вообще: ни шрифтов,
ни CDN, ни картинок — стрелка `select` нарисована инлайновым `data:`-SVG.
Соглашение по экранированию закреплено в именах параметров: `text`/`label`/`value` —
простой текст, функция экранирует сама; суффикс `_html` — готовая разметка под

## 2.3 Приём placement-POST

Битрикс шлёт `application/x-www-form-urlencoded`: часть в query (`DOMAIN`, `PROTOCOL`,
`LANG`, `APP_SID`), часть в теле (`AUTH_ID`, `AUTH_EXPIRES`, `REFRESH_ID`, `SERVER_ENDPOINT`,
`APPLICATION_TOKEN`, `APPLICATION_SCOPE`, `member_id`, `status`, `PLACEMENT`,
`PLACEMENT_OPTIONS`). FastAPI-эндпоинт принимает **форму, а не JSON**; `PLACEMENT_OPTIONS`
парсится как JSON-строка.

Порядок обработки:

1. `member_id` → `resolve_tenant_by_member_id()`.
2. Constant-time сверка `APPLICATION_TOKEN`.
3. **`SERVER_ENDPOINT` игнорируется** — хосты только из allowlist (инвариант И-4).
4. `AUTH_ID` и `REFRESH_ID` сохраняются как токены этого пользователя.
   `authorized_tg_user_id` заполняется **только** при завершении привязки через deep-link.
5. Рендер страницы с `frame-ancestors https://<домен этого портала>` — динамически,
   не общим `*.bitrix24.ru`.
6. Сессия страницы — короткоживущий JWT во фрагменте URL, `location.hash` очищается сразу
   после чтения.

## 2.4 Привязка сотрудника — основной сценарий

Телефон заполнен у 5 сотрудников из 27, поэтому путь через placement — не запасной, а главный:

```
1. Сотрудник открывает приложение в Битриксе (левое меню или вкладка проекта)
2. Мы уже знаем, кто он: placement-POST принёс его AUTH_ID и ID пользователя
3. Он нажимает «Привязать Telegram»
4. Открывается t.me/<бот теннанта>?start=b<токен>   (16 случайных байт, TTL 15 минут)
5. Он нажимает /start в личке бота
6. tg_user_id связывается, b24_user_tokens.authorized_tg_user_id = его tg_user_id
7. Статус authorized. Бот пишет: «Готово, теперь вы можете создавать задачи из чатов»
```

Если он открыл приложение с телефона, где Telegram установлен, — переход мгновенный.
С десктопа показываем QR-код на ту же ссылку.

## 2.5 Администраторы теннанта — экран и правила

Реализовано 16.08.2026 в `app_ui._admins_block` / `app_ui.role_action`.

**Зачем.** До этого экрана роль `tenant_members.role` существовала в схеме и не
проверялась нигде: `/bind` требовал только привязанного аккаунта, то есть привязать
чат к проекту мог любой сопоставленный человек — включая сотрудника клиента, у
которого тоже есть личный токен. Матрица прав ([40-security.md](40-security.md) §3)
всё это время требовала `tenant_admin`.

**Кто может назначать:**

| Кто | Может менять роли | Почему |
|---|:-:|---|
| Администратор портала Б24 | ✅ всегда | он поставил приложение; отнимать это право внутри нашего интерфейса — фикция, он переустановит. Плюс это единственный способ выдать права первому админу |
| Действующий `tenant_admin` | ✅ | обычный рабочий путь |
| Остальные | — | список видят, кнопок нет |

Права администратора портала мы **не выдаём, а спрашиваем** у Битрикса методом
`user.admin` при каждом входе — подделать нельзя, менять у себя нечего.

**Бутстрап.** Курица и яйцо решается так: при входе в приложение администратор портала
подтягивается до `tenant_admin` автоматически (`access.promote_portal_admin`), один раз,
с записью в аудит. Обратного действия нет: снятие прав администратора в самом Битриксе
роль у нас не отбирает — это делается явно на этом экране. Иначе изменение прав в портале
молча ломало бы работающую интеграцию.

**Три правила, каждое из-за конкретного способа выстрелить себе в ногу:**

1. **Последнего админа снять нельзя.** Иначе теннант остаётся без управления, и вернуть
   его можно только руками в базе. Кнопка выключена, а проверка повторяется на сервере
   под тем же локом строки — два одновременных снятия иначе обнулили бы список.
2. **Нельзя назначить того, кто не привязал Telegram.** Права без личного токена — пустая
   строка в таблице: действовать в Битриксе такому админу нечем.
3. **Право проверяется в обработчике, а не только при отрисовке кнопки.** Форму можно
   отправить и без кнопки, а роль могли понизить за время жизни страницы.

Имена сотрудников тянутся с портала одним `batch` из `user.get`: без них список выглядит
как «Битрикс24 #7», и назначать по такому списку права страшно. Отказ портала не ломает
экран — подписи деградируют до номеров.

Каждая смена роли пишется в `audit_log` как `high_risk` с полным `detail`: кто, кому,
что было и что стало. Вопрос «кто выдал этому человеку права» обязан иметь ответ.

## 2.7 Конструктор опросника — экран и правила

Реализовано 16.08.2026 в `api/app_survey.py`. Открывается кнопкой «Настроить опросник»
с главного экрана. Доступ — как у экрана администраторов (§2.5): опросник определяет,
что увидит клиент в чате и куда уедут поля задачи.

**Что на экране:**

```
Опросник
[🔴 Ничего не работает · 5] [⚠️ Работает неправильно · 5] [🔑 Нужны доступы ✎ · 7]
Новый набор: [__________] (Создать)

🔑 Нужны доступы
 1. Кому нужен доступ: имя и должность.    текстом              → в тело задачи   ↓ изменить удалить
 …
 6. Насколько срочно?                      список · обязательный → PRIORITY        ↑ ↓ изменить удалить
    Горит = 2 · Обычное = 1 · Можно позже = 0

Новый вопрос
 Текст вопроса   [___________________________]
 Тип ответа [текстом ▾]  Поле задачи [— в тело задачи — ▾]  Обязательный [нет ▾]
 Варианты ответа, по одному в строке
 [Высокий = 2                    ]
```

**Формат вариантов — `подпись = значение`.** Слева то, что человек увидит на кнопке,
справа то, что уйдёт в Битрикс. Без знака равенства подпись и значение совпадают — для
строкового поля это ровно то, что нужно. Для enum-поля под формой показывается подсказка
с допустимыми значениями прямо с портала: `Высокий = 2, Средний = 1, Низкий = 0`.

**Список полей — с портала, не зашитый.** UF-поля у каждого портала свои
(00-portal-facts.md §13). Сужается allowlist-ом: из 67 полей задачи под ответ человека
годятся единицы. Если поле, к которому вопрос был привязан, исчезло с портала, оно
показывается в списке как «нет на портале», а не подменяется молча на «в тело задачи».

**Системный набор форкается, а не правится.** `tenant_id IS NULL` — набор, общий на всю
инсталляцию; правка одного теннанта меняла бы опросник всем. Первое изменение копирует
набор себе вместе с вопросами и сохраняет `code`, поэтому копия сразу перекрывает
системный: чтение выбирает `DISTINCT ON (code) … ORDER BY tenant_id NULLS LAST`.
Об этом написано прямо на экране, до нажатия.

**Код вопроса стабилен** и не меняется при переименовании: по нему хранится ответ в
`survey_sessions.answers`, и переименование вопроса на середине опроса не должно
обнулять уже данные ответы.

**Навигация формами, а не ссылками.** Сессия страницы лежит в POST-теле: в GET-параметре
она попадала бы в логи, историю браузера и Referer.

Пределы видны настройщику: 30 вопросов в наборе, 20 вариантов на вопрос.

### Создание поля прямо из формы вопроса

В списке полей есть пункт **«➕ создать новое поле в Битрикс24»**. Рядом — поле
«Название нового поля». При сохранении вопроса поле заводится на портале:

| Тип ответа | Что создаётся |
|---|---|
| выпадающий список | UF-поле `enumeration` с этими же вариантами |
| текстом | UF-поле `string` |

Имя генерируется транслитерацией подписи с префиксом `UF_SD_` (support desk — сразу
видно, чьё поле): «Срочность» → `UF_SD_SROCHNOST`. Занятое имя получает суффикс `_2`,
потому что Битрикс на дубль отвечает `ERROR_CORE`.

**Поле появляется у всех задач портала, а не только в этом проекте.** У задач Битрикс24
пользовательские поля общие (`ENTITY_ID=TASKS_TASK`), привязки к группе не существует.
Это написано прямо под формой — до нажатия, а не после.

Для списка сразу после создания читаются ID элементов, и варианты вопроса сохраняются
как `подпись → ID`. Это обязательно: запись подписи вместо ID кладёт в поле `0` без
единого сообщения об ошибке (00-portal-facts.md §14.1).

**Сверка на каждом сохранении.** Если вопрос уже привязан к UF-списку и настройщик дописал
вариант, которого в поле нет, недостающие досоздаются через `task.item.userfield.update`.
Не получилось — сообщение жёлтое и перечисляет варианты, ответы по которым не сохранятся.
Молча принять такой вопрос нельзя: в задаче окажется `0`.

Создание поля пишется в аудит как `b24.userfield.create`.

Без них 20–30% сотрудников не привяжутся, и это спишут на продукт, а не на процесс.

## 2.8 Подтверждение задач — экран и правила

Реализовано в `api/app_approval.py`, вкладка «Подтверждение» на главном экране. Доступ —
как у опросника (§2.7) и команды (§2.5): `can_manage_admins`, то есть админ теннанта, а не
только администратор портала — это текущая настройка рабочего процесса, а не подключение
инфраструктуры (в отличие от вкладок «Бот» и «Чаты», которые пускают только администратора
портала).

**Один проект — один блок**, список берётся из уже импортированных проектов (тех, что хоть
раз привязывались к чату во вкладке «Чаты» — отдельного каталога проектов тенанта, не
зависящего от чьего-то личного OAuth-токена, в системе нет, см. docs/20-data-model.md §16).
На каждый — четыре поля:

```
Devon SD BOT                                                      выключено
клиент DEVON
  Требовать подтверждение [нет ▾]     Ответственный [— выбрать человека — ▾]
  Стадия «подтверждена»   [— выбрать стадию — ▾]
  Стадия «отклонена»      [— выбрать стадию — ▾]
  [ ✓ Сохранить ]
```

**Обе стадии — живой список с портала** (`task.stages.get`, batch-вызовом сразу на все
проекты экрана, а не по одному: invariant «список для выбора берётся с портала» действует
и здесь). При сохранении список перечитывается заново и сверяется — стадию могли удалить
на портале между открытием страницы и отправкой формы, и запись устаревшего id тогда была
бы неотличима от рабочей настройки.

**Ответственный — только зарегистрированный пользователь.** Дропдаун берёт `tenant_members`
с `link_status='authorized'` — то есть человек с живым личным OAuth-токеном, ровно как того
требует доменная модель для любого действия над задачей. Пустой список — баннер с указанием,
что список пополнится сам после первой привязки во вкладке «Команда».

**Включить нельзя без всех трёх полей.** `enabled=true` при пустом ответственном или
незаполненной стадии отклоняется с понятным сообщением, а не сохраняется наполовину:
описано в docs/20-data-model.md §16, проверяется в `api/app_approval.py._apply`, не
констрейнтом базы.

Сохранение пишется в аудит как `task.approval.configure` (обычное действие, не
`high_risk` — само по себе оно не двигает ни одной задачи и не меняет ничьих прав; решения
`task.approval.confirm`/`.reject` — двигают, и это `high_risk`, см. docs/40-security.md §3).

## 2.9 Уведомления — экран и правила

Реализовано в `api/app_notify.py`, вкладка «Уведомления». Доступ — `can_manage_admins`,
как у §2.5, §2.7 и §2.8.

Экран отвечает на два вопроса и держит их **раздельными ручками**:

| Ручка | Что задаёт | Где хранится |
|---|---|---|
| Набор событий | о чём вообще сообщать | `notification_settings` |
| Группировка | сразу каждым сообщением или сводкой раз в N минут | `notification_digest_settings` |

Переключатели идут двумя наборами: **новости о задачах** (приходят в ответ на действие
человека в Битриксе) и **напоминания и сводка** (шлёт расписание, `domain/reminders.py`,
и, кроме утренней сводки, — в личку). Смешать их в один список значило бы ответить на
вопрос «почему бот пишет мне лично» в середине перечня про задачи. Напоминания в личку на
уровне чата не показываются: у них адресат человек, а не чат.

Сводить их в одну ручку («тихий режим») нельзя: чат может хотеть все события и при этом
не хотеть восьми сообщений подряд. Общая ручка выключала бы людям события, о которых они
просили.

**Три уровня, цепочка та же, что у всех настроек проекта** (инвариант И-9):
`чат` → `проект` → `теннант` → системный дефолт. Отсутствие записи = наследовать выше;
«выключено» пишется явным `false`, а не удалением строки.

```
Уведомления всего теннанта
  Сейчас применяется: событий: 6 из 7 · сразу, каждым сообщением.
  Набор событий [свой набор ▾]     Группировка [сразу ▾]
  О чём сообщать
    [x] Изменён статус     [ ] Создана задача     [x] Перенесена по канбану  …
  [ ✓ Сохранить ]

Проекты и чаты
  Линия Жизни Битрикс24                                     как у теннанта
  клиент Линия Жизни · событий: 6 из 7 · сразу
    ⚙ Настроить проект «Линия Жизни Битрикс24»
    💬 ЛЖ · поддержка   событий: 6 из 7 · раз в 15 минут       своя настройка
      ⚙ Настроить чат «ЛЖ · поддержка»
```

Четыре решения, которые стоит знать:

1. **Уровней три, потому что «нас заваливает» — это всегда про конкретный чат.** В одном
   чате проекта дежурная смена, которой нужно всё; в соседнем — руководитель, которому
   хватает сводки раз в час. Настройка только на проекте заставила бы выбирать за обоих.
   Раньше решение принималось один раз на проект (`events.is_enabled`), и выключить лишнее
   в одном чате означало выключить его всем.
2. **Галочки всегда показывают то, что применяется сейчас**, включая унаследованное.
   Поэтому «свой набор» без единого клика сохраняет ровно то, что человек и видел:
   уровень перестаёт наследовать, но ничего не меняет. Пустая форма на этом месте
   читалась бы как «всё выключено».
3. **Разрешение покодовое, и экран трогает ровно те коды, которые показывает.** В ту же
   таблицу пишет команда `/digest` из чата — одной строкой `digest.daily`. Правило «уровень
   целиком» отменяло бы такой строкой всю настройку проекта для этого чата, а удаление
   «по уровню» при сохранении стирало бы саму строку `/digest`. Оба случая молчаливые.
4. **Переключателя без рассылки на экране нет.** `task.comment_added` описан в реестре
   (`domain/notifications.py`), но помечен `emitted=False`: уведомление о комментарии пока
   не ставит в очередь ни один обработчик. Выключатель, ничего не выключающий, — то же
   обещание, что команда в меню, которой не знает роутер. Страж — `tests/test_notifications.py`,
   сверяет реестр с исходником `events.py` разбором `ast`.

Сохранение пишется в аудит как `notify.configure` (обычное действие: прав оно не меняет
и задач не двигает).

**Настройки уведомлений живут только здесь.** Второй вход в ту же настройку — команда в
боте или экран в мини-аппе — означал бы три реализации одной цепочки наследования, которые
разойдутся; ровно по этой причине в мини-апп не переехал `/bind`.

# Часть 3. Мини-апп Telegram

Реализовано 16.08.2026. Живёт по пути **`https://b24sdbot.devondev.ru/miniapp`** того же
домена: отдельный поддомен потребовал бы своей A-записи и своего сертификата без единой
выгоды. Фронтенд — React + Vite (`web/miniapp/`), собирается первым этапом Dockerfile
и попадает в образ статикой; node в рантайме отсутствует.

## 3.1 Зачем он, если есть бот

В чате хорошо делать одно движение: ответил на сообщение — появилась задача. Всё, где
нужен выбор из двадцати вариантов или произвольная дата, в чате превращается в лес
кнопок. Мини-апп берёт на себя именно это:

| Операция | Бот | Мини-апп |
|---|---|---|
| Список задач | текстом, 10 на страницу | фильтры, поиск, группировка по стадиям |
| Карточка | текст + кнопки действий | то же плюс комментарии на одном экране |
| Срок | 4 пресета кнопками | любая дата и время |
| Ответственный | до 12 человек кнопками | весь список участников проекта |
| Приоритет | 3 кнопки | 3 кнопки |
| Создание | заголовок из сообщения | полная форма со всеми полями |

Бот при этом ничего не потерял: редактирование срока, ответственного и приоритета
кнопками сделано и в нём (см. [30-bot-spec.md](30-bot-spec.md) §6.1).

## 3.2 Как он открывается — и почему именно так

Ручных шагов у теннанта **ноль**. Кнопку меню бота приложение ставит само вызовом
`setChatMenuButton` при подключении бота и при каждой проверке связи.

| Откуда | Механизм | Ограничение Telegram |
|---|---|---|
| Личка бота, кнопка меню | `setChatMenuButton` с `web_app` | ставится через Bot API; **обязательно с `chat_id`** — см. ниже |
| Личка бота, нижняя клавиатура | `KeyboardButton.web_app` | только в личных чатах |
| Групповой чат, кнопка под сообщением | ссылка `t.me/<бот>?start=a<контекст>` → бот присылает в личку кнопку `web_app` | **кнопки `web_app` в группах запрещены Telegram**, это ограничение клиента |
| Групповой чат, если заведено имя приложения | `t.me/<бот>/<имя>?startapp=<контекст>` — открывается в одно касание | требует `/newapp` в BotFather, **необязательно** |

**Кнопку меню нужно ставить адресно.** `setChatMenuButton` без `chat_id` задаёт
умолчание для всех личных чатов, возвращает `True` — и не показывает кнопку, если у бота
настроено меню команд: `getChatMenuButton` продолжает отвечать `commands`. Проверено на
живом `@devon_sd_bot` 16.08.2026. С `chat_id` кнопка ставится и читается обратно, поэтому
она ставится ещё раз на `/start` и при завершении привязки — там личный чат уже известен.

Короткое имя из BotFather — единственный ручной шаг во всей цепочке, и он лишь убирает
один переход. Хранится в `tg_bots.miniapp_short_name`, вводится на экране приложения
в Битрикс24, запасное значение — `MINIAPP_SHORT_NAME` в окружении.

## 3.3 Контекст чата

Из `initData` чат узнать нельзя: Telegram присылает `chat_type` и `chat_instance`,
по которым чат не опознать. Поэтому контекст передаём мы сами — **подписанной строкой**
`<chat_ref>-<thread>-<task>-<HMAC16>` на `MASTER_KEY`:

* из группы она уезжает в `startapp` и приходит внутри подписи Telegram;
* через личку — в `?ctx=` адреса страницы (в кнопку `web_app` `startapp` не положить).

Строка не даёт доступа: она лишь называет чат. Кто перед нами, решает подпись Telegram;
что ему можно — личный токен Битрикса. Подмена номера чата в строке ломает HMAC и
отвергается (`test_packed_context_rejects_forged_chat`).

Строк в базе на каждую кнопку при этом не появляется — в отличие от `callback_tokens`,
где наружу уходит случайное значение, а внутри лежит его sha256, и одну и ту же ссылку
из базы не восстановить.

**В личке контекста нет**, поэтому мини-апп показывает выбор чата — только чатов своего
теннанта и только с проектами, которые человек видит в портале (`sonet_group.user.groups`).
Ссылка из группы «прибивает» чат намертво: сменить его в этом режиме нельзя, иначе кнопка
в чате одного клиента открывала бы задачи другого.

## 3.4 Аутентификация

Заголовок `Authorization: tma <initData>` на каждом запросе, сверка HMAC по алгоритму
Telegram при каждом обращении. Своей сессии нет намеренно: строка Telegram и так
подписана и протухает, а лишняя таблица сессий — ещё одно место, где можно забыть
`tenant_id` (И-2). Подробности и модель угроз — [40-security.md](40-security.md) §7.1.

Теннант определяется тем, **чьим токеном сошлась подпись**. Кандидаты подбираются по
чату из `startapp` и по членству пользователя; если ни одного нет (человек ещё не
привязан и пишет в личку) — перебираются активные боты, не более 25.

## 3.5 Контракт API

Префикс `/api/miniapp`. Формат ошибки общий с панелью:
`{"error": {"code": "...", "message": "...", "details": {...}}}`.

| Метод и путь | Что делает |
|---|---|
| `GET /bootstrap` | кто я, портал, контекст чата. Непривязанный аккаунт — не ошибка, а состояние `not_linked` |
| `GET /contexts` | чаты на выбор (личный режим) |
| `GET /tasks?chat_ref=&filter=&q=&project_id=` | список; `filter` = `all\|mine\|overdue\|closed` |
| `GET /tasks/{id}` | карточка: блок `allowed` из ответа портала, `stage_title`, `time_spent` (секунды списаний) |
| `POST /tasks/{id}/action` | `complete\|start\|pause\|defer\|renew` спец-методами |
| `PATCH /tasks/{id}` | заголовок, описание, срок, приоритет, ответственный, стадия |
| `GET /tasks/{id}/comments` · `POST` | обсуждение задачи |
| `POST /tasks` | создание полной формой |
| `GET /projects/{id}/members` · `/stages` | справочники для формы |
| `GET /approvals` | задачи, ждущие подтверждения ЭТОГО человека — единственный путь без `chat_ref`, решение не привязано к чату (§2.8) |
| `POST /approvals/{id}/action` | `{"decision": "confirm"\|"reject"}` |
| `GET /summary` | сводка по стадиям канбана — числа те же, что в «📊 Сводке» бота |
| `GET /timesheet/months` · `GET /timesheet?month=` | свод трудозатрат за месяц: разрезы по статусам и по стадиям |
| `GET /surveys` · `GET /surveys/{id}` | наборы вопросов и сами вопросы — те же шаблоны, что у `/ask` |
| `POST /tasks/{id}/files` | вложения, `multipart/form-data`, поле `files` |
| `GET /me` | `/whoami` бота: теннант, портал, роль |

**Паритет с ботом — не совпадение, а требование** (20.08.2026). Всё, что бот умеет
командами и кнопками, умеет и мини-апп; человек, привыкший к одному интерфейсу, не
должен упираться в другом в отсутствующую функцию и гадать, потерялась она или её не
было. Логика при этом **переиспользуется, а не переписывается**: трудозатраты считает
`domain/timesheet`, сводку — `bot/views`, ответы опросника разбирает `bot/survey.assemble`.
Разъедься реализации — одно и то же считалось бы в боте и в приложении по-разному, а это
худший вид расхождения: оба ответа выглядят одинаково уверенно.

Что различается намеренно:

* **Опросник задаёт все вопросы сразу.** В чате они идут по одному, потому что диалог
  линеен; на экране их видно списком — можно вернуться, поправить ответ, не начиная
  заново, и понять, сколько осталось, ещё до первого ответа. Шаблоны, привязка ответов
  к полям задачи и правило «ответ, который поле не приняло, уходит в тело» — общие.
* **Вложения приходят из браузера, а не из Telegram.** Ключ идемпотентности — sha256
  содержимого: `file_id` здесь взять неоткуда, а повторная отправка формы после таймаута
  не должна класть в задачу второй такой же файл (И-10). Пределы (10 файлов, 20 МБ,
  чёрный список расширений) — общие с ботом, чтобы «20 МБ» значило одно и то же.
  Файлы отсеиваются **до** обращения к порталу: искать папку ради того, чтобы ничего
  в неё не положить, — лишний поход против лимита частоты.
* **Привязку чата (`/bind`, `/unbind`) мини-апп не делает.** Она уже живёт в двух местах —
  команда в чате и экран внутри портала (§2.2); третья точка для той же операции
  означала бы три реализации, которые разойдутся.

Коды ошибок: `401 unauthenticated`, `403 not_linked` / `forbidden` / `needs_reauth` /
`b24_forbidden`, `404 not_found`, `409 no_project`, `429 rate_limited`,
`400 validation`, `502 upstream_error`.

**`stage_title` считает сервер, а не приложение** (18.08.2026). Портал в задаче отдаёт
только `stageId`, поэтому в карточке стояло бы «335». Название разрешается по справочнику
`project_stages` тем же кодом, что и в боте (`views.resolve_stage_title`), с точечным
обновлением справочника, если стадия незнакома. Форма правки при этом берёт список колонок
живьём с портала (`GET /projects/{id}/stages`): справочник — для показа, портал — для выбора.

Правила, действующие в каждом обработчике:

1. **И-3 без исключений.** Любое обращение к задаче проходит `authorize_task_for_chat`,
   и отказ всегда один — «задача не найдена в проектах этого чата». «Нет прав» и «нет
   задачи» отвечают одинаково, иначе перебор номеров работает как оракул.
2. **Границу выборки задаёт `GROUP_ID`.** Сервисной учётки с урезанной видимостью нет,
   поэтому список задач без фильтра по группам чата не уходит в портал никогда.
3. **Личный токен человека.** Права режет портал; блок `action` из ответа определяет,
   какие кнопки показывать.
4. **Срок только с явным offset.** Дата без часового пояса — ошибка ввода: у каждого
   портала свой пояс, и угадывать его мы не имеем права.
5. **После записи — перечитать и сверить.** Битрикс молча игнорирует непринятое; поля,
   которые не применились, возвращаются в `not_applied` и показываются человеку.
6. **Идемпотентность создания.** Форма несёт `form_id`, из него собирается `idem_key`
   (И-10): повторная отправка после таймаута не создаёт вторую задачу.

## 3.6 Экраны

```
Загрузка → не привязан            → инструкция и кнопка «я привязал, проверить»
        → нет контекста (личка)   → выбор чата
        → список задач            → фильтры, поиск, стадии, дерево подзадач
             ├── карточка         → поля, действия, правка листом, файлы, комментарии
             ├── новая задача     → полная форма ИЛИ опросник по вопросам
             ├── сводка           → задачи по стадиям, числа кликабельны
             ├── трудозатраты     → месяц кнопками, разрезы по статусам и стадиям
             ├── о приложении     → «кто я», проекты чата, что умеет
             └── на подтверждении → колокол со счётчиком в шапке списка;
                                     единственный экран без `context` — задачи
                                     по всему теннанту, а не текущего чата (§2.8)
```

Шапка списка несёт две кнопки: колокол со счётчиком ожидающих решения и «⋯».
Разделов шесть, и все шесть иконками в шапку не влезают — при 44px на цель это 264px
из 375px ширины, заголовку чата не остаётся ничего. Наружу вынесено то, что несёт
**счётчик**: спрятанный в меню счётчик не сообщает ничего.

У каждого экрана обязательны четыре состояния: загрузка, пусто с объяснением, ошибка
с кодом и кнопкой «повторить», нет прав без раскрытия существования объекта
(`src/components/States.tsx` — вынесены именно затем, чтобы их нельзя было забыть).

Оформление берётся из темы клиента Telegram: своя палитра поверх тёмной темы выглядела
бы чужеродной ровно там, где приложение обязано быть частью мессенджера. HTML из данных
не собирается нигде — React экранирует текст сам, `dangerouslySetInnerHTML` не
используется (И-6 по построению).

**Токены, контраст, цели касания и правила взаимодействия — в отдельном документе:
[55-miniapp-design.md](55-miniapp-design.md).** Там же стенд, которым это меряется,
и обоснование каждого отступления от норм.
