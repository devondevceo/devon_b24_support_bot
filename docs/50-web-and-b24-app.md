# Веб-панель и приложение внутри Битрикс24

Два интерфейса к одним и тем же операциям. **Набор операций один**, и он обязан совпадать
с админ-командами бота из [30-bot-spec.md](30-bot-spec.md) §9 — иначе интерфейсы разъедутся
и начнут делать разное.

Разделение обязанностей:

| Где | Что делается | Почему именно там |
|---|---|---|
| **Приложение в Б24** | привязка сотрудника, привязка проекта к чату из карточки проекта, статус интеграции | там уже есть контекст (кто ты, какая группа) и там сидят сотрудники теннанта |
| **Веб-панель** | всё управление: теннанты, клиенты, проекты, привязки, дефолты, уведомления, пользователи, аудит | нужны таблицы, фильтры и второй фактор |
| **Бот** | быстрые операции в контексте чата: `/bind`, `/notify`, `/health` | рука уже в чате |

# Часть 1. Веб-панель

Стек: React + Vite, собирается в CI, на сервер приезжает готовый `dist`, отдаётся FastAPI
за Traefik. Язык — русский.

## 1.1 Аутентификация

Два входа, оба ведут к одной сессии:

**Telegram Login Widget.** При модели «свой бот у каждого теннанта» виджет нельзя привязать
к боту теннанта: `client_id` виджета — это конкретный бот, а `redirect_uri` регистрируется
в BotFather его владельцем, то есть теннантом. Решение: **вход через единый бот DEVON**
(`@devon_support_login_bot`), домен зарегистрирован нами один раз. Бот теннанта для входа
не используется вообще. Он же служит аварийным каналом уведомлений.

**Логин и пароль.** Argon2id, блокировка после серии неудач. Нужен, когда Telegram недоступен.

**TOTP обязателен для `tenant_admin` и `devon_superadmin`** (обоснование — [40-security.md](40-security.md) §13).

**Сессия** — httpOnly-кука, срок 12 часов, `web_sessions` с полем `session_epoch`. Роль
читается из БД на каждом запросе; при смене роли или пароля `users.session_epoch`
инкрементируется и все сессии умирают.

### Жизненный цикл учётной записи

SMTP в проекте нет и не планируется, поэтому доставка — через бота DEVON в личку:

1. Суперадмин создаёт админа теннанта, указывая его `tg_user_id` (или приглашая по
   одноразовой ссылке).
2. Приглашённый получает в личке бота DEVON ссылку с одноразовым токеном, TTL 30 минут.
3. Первый вход — принудительная установка пароля и подключение TOTP.
4. Сброс пароля — тем же каналом. Кода в чат не пишем, только ссылку.
5. При отзыве доступа — `session_epoch++`, все сессии мгновенно недействительны.

**Бутстрап первого суперадмина.** При пустой таблице `users` стартовый хук создаёт
суперадмина из `SUPERADMIN_TG_USER_ID` в окружении и печатает в лог одноразовый код привязки.
После первого успешного входа переменная окружения игнорируется навсегда.

## 1.2 Карта экранов

```
Вход
└── Дашборд
    ├── Теннанты (только суперадмин)
    │   └── Карточка теннанта
    │       ├── Портал Битрикс24
    │       ├── Telegram-бот
    │       ├── Клиенты
    │       │   └── Карточка клиента → Проекты
    │       ├── Проекты
    │       │   └── Карточка проекта → Привязки, Дефолты полей
    │       ├── Привязки чат ↔ проект
    │       ├── Уведомления
    │       ├── Пользователи и сопоставления
    │       ├── Аудит
    │       └── Здоровье интеграции
    └── Профиль (пароль, TOTP, сессии)
```

Админ теннанта попадает сразу в карточку своего теннанта, раздел «Теннанты» ему не виден.

Каждый экран обязан иметь четыре состояния: **загрузка**, **пусто** (с объяснением, что
сделать), **ошибка** (с кодом и кнопкой «повторить»), **нет прав** (без раскрытия
существования объекта).

## 1.3 Экраны

**Дашборд.** Плитки: активных чатов, привязанных проектов, задач создано за неделю,
непривязанных сотрудников, состояние интеграции (зелёный/жёлтый/красный), очередь.
Для суперадмина — то же в разрезе теннантов.

**Теннанты** (суперадмин). Таблица: название, портал, бот, клиентов, чатов, статус,
последняя активность. Действия: создать, приостановить, удалить (с подтверждением вводом
названия — процедура удаления в [40-security.md](40-security.md) §14).

**Портал Битрикс24.** Показывает: домен, `member_id`, состояние установки приложения,
выданные scope, срок жизни токена установщика, сервисные учётки (`service_admin`,
`service_reader`) с состоянием. Действия: «Установить приложение» (даёт ссылку и инструкцию),
«Переустановить», «Назначить сервисного читателя», «Проверить подключение» (живой вызов
`app.info` с показом результата).

**Telegram-бот.** Поле ввода токена — **единственное место в системе, где токен вводится**
(в чат его писать запрещено). При сохранении: `getMe`, проверка занятости `bot_id`, установка
вебхука. Показывает: username, состояние вебхука («настроен» / «не настроен» — **без вывода
URL**), режим (webhook/polling), последняя проверка. Действия: «Перевыпустить вебхук»,
«Проверить», «Отключить».

**Клиенты.** Таблица: название, компания в CRM, проектов, чатов, статус. Создание: название
плюс выбор компании из CRM через поиск по `crm.company.list` (на портале их 2094, поэтому
именно поиск, а не выпадающий список). Связь используется в карточке задачи, в сводках
и во вкладке компании в CRM — если бы не использовалась, поле и вкладку следовало бы убрать.

**Проекты.** Кнопка «Импортировать из Битрикс24» тянет `sonet_group.get` и показывает группы
чекбоксами с уже импортированными в неактивном состоянии. Таблица: название, ID группы,
клиент, тип, экстранет, чатов, задач в кэше, состояние синхронизации.

**Карточка проекта.** Стадии канбана (только чтение, синхронизируются из Б24), дефолты полей
задачи, привязанные чаты, кнопка «Синхронизировать сейчас».

**Привязки.** Таблица: чат, топик, проект, клиент, кто привязал, когда, состояние.
Чат выбирается **только из списка тех, где бот реально присутствует** — ручной ввод `chat_id`
запрещён (обоснование — [40-security.md](40-security.md) §4). Проверка «все проекты чата
принадлежат одному клиенту» выполняется до сохранения с внятным сообщением.

**Дефолты полей задачи.** Форма на уровне теннанта и на уровне проекта: ответственный,
приоритет, срок «+N дней», наблюдатели, соисполнители, стадия. У каждого поля три состояния:
**наследовать**, **задать значение**, **сбросить**. UI обязан писать явный `false`/`null`,
а не удалять запись (инвариант И-9).

**Уведомления.** Матрица «код события × уровень (теннант / проект / привязка)» с тремя
состояниями в каждой ячейке: наследовать, включено, выключено. Отдельно видно, откуда
унаследовано текущее значение.

**Пользователи и сопоставления.** Таблица: имя в Telegram, `tg_user_id`, пользователь Б24,
статус (`none` / `matched` / `authorized` / `needs_reauth`), когда привязан, последняя
активность. Действия: пригласить (ссылка в личку), сопоставить вручную (**даёт только
`matched`**), снять сопоставление, отправить напоминание о переавторизации.
Отдельный счётчик «сколько сотрудников не привязано» — это метрика онбординга, а не дефект.

**Аудит.** Фильтры: период, пользователь, действие, клиент, проект, только высокорисковые.
Экспорт в CSV с экранированием формул. Режим аудита переключается здесь же, с явным
предупреждением, что `minimal` вступит в силу через 24 часа.

**Здоровье интеграции.** Состояние портала, вебхуков, подписок на события, очередей,
свежести кэша, свободного диска. Кнопки: «Проверить всё», «Пересоздать подписки»,
«Принудительная синхронизация». Здесь же — предупреждения вида «событий не приходило 24 часа».

## 1.4 Контракт API

Все ответы — JSON. Ошибка: `{"error": {"code": "...", "message": "...", "details": {...}}}`.
Коды: `400 validation`, `401 unauthenticated`, `403 forbidden`, `404 not_found`,
`409 conflict`, `429 rate_limited`, `502 upstream_error` (Битрикс или Telegram).
Списки: `?page=1&per_page=50&q=&sort=`, ответ `{"items": [...], "total": N, "page": 1}`.

| Метод и путь | Роль | Что делает |
|---|---|---|
| `POST /api/v1/auth/telegram` | — | вход по подписи Login Widget |
| `POST /api/v1/auth/password` | — | вход по паролю |
| `POST /api/v1/auth/totp` | — | подтверждение второго фактора |
| `POST /api/v1/auth/logout` | любая | завершить сессию |
| `GET /api/v1/me` | любая | профиль, роль, теннант |
| `GET /api/v1/me/sessions` · `DELETE /api/v1/me/sessions/{id}` | любая | список и отзыв сессий |
| `GET /api/v1/tenants` · `POST` | superadmin | список, создание |
| `GET /api/v1/tenants/{id}` · `PATCH` · `DELETE` | superadmin | карточка, изменение, удаление |
| `GET /api/v1/tenants/{id}/portal` | admin | состояние портала |
| `POST /api/v1/tenants/{id}/portal/check` | admin | живой `app.info` |
| `POST /api/v1/tenants/{id}/portal/service-user` | admin | назначить `service_reader` |
| `GET /api/v1/tenants/{id}/bot` · `PUT` · `DELETE` | admin | бот теннанта, ввод токена |
| `POST /api/v1/tenants/{id}/bot/rewebhook` | admin | перевыпустить вебхук |
| `GET /api/v1/clients` · `POST` · `PATCH /{id}` · `DELETE /{id}` | admin | клиенты |
| `GET /api/v1/crm/companies?q=` | admin | поиск компании в CRM |
| `GET /api/v1/projects` · `PATCH /{id}` | admin | проекты |
| `POST /api/v1/projects/import` | admin | импорт групп из Б24 |
| `POST /api/v1/projects/{id}/sync` | admin | принудительная синхронизация |

| `GET /api/v1/chats` | admin | чаты, где присутствует бот |

| `GET /api/v1/defaults?scope=` · `PUT` | admin | дефолты полей задачи |
| `GET /api/v1/notifications?scope=` · `PUT` | admin | настройки уведомлений |

| `GET /api/v1/health` | admin | здоровье интеграции |
| `POST /api/v1/health/resubscribe` | admin | пересоздать подписки |

**IDOR.** Каждый обработчик резолвит объект **вместе с `tenant_id` из сессии** одним запросом,
а не «сначала достать, потом проверить». Отсутствие прав и отсутствие объекта дают одинаковый
`404`, кроме случаев, когда объект заведомо принадлежит запросившему.

# Часть 2. Приложение внутри Битрикс24

## 2.1 Установка

Тип — локальное серверное приложение, регистрирует администратор портала теннанта.

Мастер установки **обязан быть идемпотентным**: падение на середине не должно оставлять
теннанта в застрявшем состоянии, повторный запуск должен доводить установку до конца.

```
1. ONAPPINSTALL → сохранить member_id, домен, APPLICATION_TOKEN, токены установщика
                  как service_admin
2. placement.bind × 4 (см. 2.2)
3. event.bind на ONTASKADD, ONTASKUPDATE, ONTASKDELETE, ONTASKCOMMENTADD,
                ONAPPUPDATE, ONAPPUNINSTALL, ONAPPTEST
4. BX24.installFinish()   ← без него приложение считается неустановленным:
                            виджеты не показываются, события не приходят вообще
5. tenants.install_state = 'finished'
```

**`ONAPPUPDATE` перезаписывает `APPLICATION_TOKEN` и заново вызывает весь набор `event.bind`.**
Токен меняется при обновлении приложения, а обработчики событий при этом удаляются. Не сделать
этого — значит тихо перестать принимать события с полностью чистыми логами. Покрыто отдельным
тестом; плюс суточный `reconcile_events` сверяет подписки через `event.get` токеном
администратора и досоздаёт недостающие.

## 2.3 Приём placement-POST

Битрикс шлёт `application/x-www-form-urlencoded`: часть в query (`DOMAIN`, `PROTOCOL`,
`LANG`, `APP_SID`), часть в теле (`AUTH_ID`, `AUTH_EXPIRES`, `REFRESH_ID`, `SERVER_ENDPOINT`,
`APPLICATION_TOKEN`, `APPLICATION_SCOPE`, `member_id`, `status`, `PLACEMENT`,
`PLACEMENT_OPTIONS`). FastAPI-эндпоинт принимает **форму, а не JSON**; `PLACEMENT_OPTIONS`
парсится как JSON-строка.

Порядок обработки:

1. `member_id` → `resolve_tenant_by_member_id()`.
2. Constant-time сверка `APPLICATION_TOKEN`.
3. **`SERVER_ENDPOINT` игнорируется** — хосты только из allowlist (инвариант И-4).
4. `AUTH_ID` и `REFRESH_ID` сохраняются как токены этого пользователя.
   `authorized_tg_user_id` заполняется **только** при завершении привязки через deep-link.
5. Рендер страницы с `frame-ancestors https://<домен этого портала>` — динамически,
   не общим `*.bitrix24.ru`.
6. Сессия страницы — короткоживущий JWT во фрагменте URL, `location.hash` очищается сразу
   после чтения.

## 2.4 Привязка сотрудника — основной сценарий

Телефон заполнен у 5 сотрудников из 27, поэтому путь через placement — не запасной, а главный:

```
1. Сотрудник открывает приложение в Битриксе (левое меню или вкладка проекта)
2. Мы уже знаем, кто он: placement-POST принёс его AUTH_ID и ID пользователя
3. Он нажимает «Привязать Telegram»
4. Открывается t.me/<бот теннанта>?start=b<токен>   (16 случайных байт, TTL 15 минут)
5. Он нажимает /start в личке бота
6. tg_user_id связывается, b24_user_tokens.authorized_tg_user_id = его tg_user_id
7. Статус authorized. Бот пишет: «Готово, теперь вы можете создавать задачи из чатов»
```

Если он открыл приложение с телефона, где Telegram установлен, — переход мгновенный.
С десктопа показываем QR-код на ту же ссылку.

## 2.5 Материалы онбординга

Без них 20–30% сотрудников не привяжутся, и это спишут на продукт, а не на процесс.
Готовятся вместе с приложением, а не «потом»:
