# devon_b24_support_bot

Telegram-бот и мини-апп для работы с задачами Битрикс24 из общих чатов поддержки.
Разработчик — компания DEVON. Пилот: теннант DEVON, клиент «Линия Жизни».

## Доменная модель

**Теннант** — компания, оказывающая поддержку. У него ровно один портал Битрикс24 и свой
Telegram-бот. У теннанта много **клиентов**; у клиента один или несколько **проектов**
(рабочих групп в Битриксе теннанта). Проект привязывается к одному или нескольким
**чатам Telegram**; один чат может быть привязан к нескольким проектам, но обязательно
**одного клиента**. Чат принадлежит ровно одному теннанту.

Люди в чате — вперемешку сотрудники клиента и сотрудники теннанта. Создавать и редактировать
задачи может только тот, кто **сопоставлен** с пользователем Битрикса и имеет живой личный
OAuth-токен. Права режет сам Битрикс, мы их не расширяем.

Роли: суперадмин DEVON → админ теннанта → пользователь. Роли «админ клиента» нет.

## Жёсткие инварианты

Нарушение любого из них — это баг с последствиями, а не стилистическое замечание.
У каждого указано, чем проверяется.

**И-1. Сырой `Update` Telegram не попадает в БД.**
Privacy mode выключен, бот видит всю переписку. Попадание апдейта в очередь означает переписку
сотрудников клиента в таблице, в WAL и в бэкапах.
*Проверяется:* канареечный тест — уникальная строка из сообщения не находится полнотекстовым
поиском ни в одной таблице.

**И-2. `tenant_id` обязателен в каждом запросе к доменным таблицам.**
Исключений нет, включая `outbox`, `callback_tokens`, `tg_fsm_states`.
*Проверяется:* тест-страж сверяет список таблиц из миграций со списком таблиц, имеющих
`tenant_id`; расхождение валит сборку. Плюс тесты изоляции двух теннантов.

**И-3. Любой доступ к задаче — только через `authorize_task_for_chat`.**
`/t_<id>`, `/comment`, ввод номера, ввод URL, любой callback. Задача обязана
принадлежать проекту, привязанному к этому чату. Отказ всегда одинаковый — «задача не найдена
в проектах этого чата», иначе работает оракул существования.
*Проверяется:* тест на перебор номеров задач из чата другого клиента.

**И-4. Хосты внешних вызовов — только из allowlist, никогда из входящих данных.**
`SERVER_ENDPOINT` и `client_endpoint` в placement-POST формирует браузер пользователя портала.
`client_endpoint` собираем сами из `tenants.b24_domain`.
*Проверяется:* тест на подмену `SERVER_ENDPOINT`.

**И-5. Обновление токена — только под `pg_advisory_xact_lock`.**
Сессионный лок в asyncio виснет при отмене задачи. `refresh_token` одноразовый: ноль
обновлённых строк в `UPDATE ... RETURNING` — это инцидент и `needs_reauth`, а не молчаливый
возврат токена.
*Проверяется:* тест с пятью параллельными обновлениями и отменой одного на середине.

**И-6. Все подстановки экранируются: `esc_html()` для Telegram, `esc_bbcode()` для Битрикса.**
Без исключений — включая имена людей, названия чатов, имена файлов и данные, пришедшие из
Битрикса. Bidi-символы (U+202A–U+202E, U+2066–U+2069) удаляются из имён файлов.
*Проверяется:* property-тест — рендер карточки с именами из полного набора спецсимволов не
даёт ни одного лишнего тега.

**И-7. Секреты только в шифрованных колонках.**
Никогда в логах, никогда в сообщениях чата, никогда в ответах API. Токен бота вводится только
через веб-панель — набранный в чат, он уходит в облако Telegram и в историю.
*Проверяется:* скраббер логов + `gitleaks` в CI.

**И-8. `APPLICATION_TOKEN` — идентификатор портала, а не доказательство подлинности.**
Его видит любой сотрудник теннанта через F12. Ни одно деструктивное действие не выполняется
по событию без подтверждающего дозапроса нашим токеном.
*Проверяется:* тест на поддельный `ONAPPUNINSTALL`.

**И-9. Отсутствие записи в настройках = наследовать выше.**
`binding` → `project` → `tenant` → системный дефолт. UI обязан писать явный `false`, а не
удалять строку. В `mclick` отсутствие ключа трактовалось как «включено» — это стоило инцидента.
*Проверяется:* тесты разрешения настроек на всех трёх уровнях.

**И-10. Мутации в Битриксе идемпотентны.**
Перед `tasks.task.add` пишется `idem_key` в `entity_external_refs`; при ретрае сначала ищем
уже созданную задачу. Вложение со статусом `committed` не перезаливается никогда.
*Проверяется:* тест «ответ не дошёл по таймауту, ретрай не создал дубль».

## Частые ошибки при работе с API Битрикса

Все подтверждены на живом портале, см. [docs/00-portal-facts.md](docs/00-portal-facts.md):

- **Регистр разный на входе и выходе.** На вход `UPPER_SNAKE_CASE`, на выход `camelCase`.
  Нельзя переиспользовать имена полей запроса для парсинга ответа.
- **Статусов пять: 2, 3, 4, 5, 6.** Статусов «Новая» и «Отклонена» не существует.
- **`STATUS` ≠ `REAL_STATUS`.** В ответе `status` — настоящий статус, `subStatus` — тот, что
  содержит псевдостатусы `-1` просрочена, `-2` не просмотрена, `-3` почти просрочена.
  `filter[STATUS]=3` не вернёт просроченную задачу «в работе».
- **«Новые» — это стадия канбана, а не статус.** `task.stages.get(entityId=<b24_group_id>)`,
  у каждого проекта свои стадии. `STATUS` и `STAGE_ID` независимы.
- **`UF_TASK_WEBDAV_FILES` содержит ID присоединённого объекта**, а не файла на Диске.
  Читать через `disk.attachedobject.*`, `disk.file.get` вернёт `ERROR_NOT_FOUND`.
- **Поля фильтра `ACCOMPLICE` и `AUDITOR` в единственном числе**, а поля задачи — во
  множественном. Перепутать = пустая выборка без ошибки.
- **Два лимита сразу:** частота 2 запроса/с с ведром 50 и `operating` 420 с в окне 600 с.
  `batch` помогает против первого и не помогает против второго.
- **UF-поля не возвращаются даже при `select=["*"]`** — перечислять явно.
- **Смену статуса делать спец-методами** (`tasks.task.complete/start/defer/renew/delegate`),
  а не сырым `update STATUS`: они проводят бизнес-логику и права.
- **Даты слать с явным offset.** В мультитенанте у каждого портала свой часовой пояс.
- **Битрикс молча игнорирует неизвестные поля.** После любой записи — перечитать и сверить.
- **`task.elapseditem.getlist` не принимает фильтры** (`ERROR_CORE`), только полный список.
- **`event.get` через вебхук отдаёт `WRONG_AUTH_TYPE`** — события только через приложение.
- **Комментарии задач лежат в чате задачи, а не в форуме.** `task.commentitem.add` пишет,
  но `task.commentitem.getlist` всегда пуст, а `task.commentitem.get` отдаёт
  `ITEM_NOT_FOUND_OR_NOT_ACCESSIBLE`. Читать через `im.dialog.messages.get` с
  `DIALOG_ID='chat<chatId>'`, отфильтровывая системные сообщения с `author_id=0`.
  `COMMENTS_COUNT` не заполняется.
- **`TAGS` нет в `getFields`, но метод его принимает.** Возвращается объектом
  `{"7": {"id":7,"title":"..."}}`, а не массивом. Поле фильтра — `TAG` в единственном числе.
  На теге строится идемпотентность создания задач.
- **Квадратные скобки в тексте съедаются как BBCode** — ещё одна причина, почему `esc_bbcode`
  обязателен на всех подстановках без исключения.

## Частые ошибки, найденные на живом сервере

- **httpx на уровне INFO печатает полный URL запроса**, а токен Telegram лежит прямо
  в пути (`/bot<id>:<секрет>/getUpdates`). Через минуту после первого запуска токен бота
  оказался в json-логах контейнера. Лечится скраббером `core/logging.py` и понижением
  уровня логгера httpx до WARNING. **Любая новая библиотека проверяется на это же.**
- **Telegram на этом хосте недоступен в обе стороны**: и мы до `api.telegram.org`,
  и его серверы до нашего домена. Приём апдейтов — long polling через SOCKS5,
  схема обязательно `socks5h` (резолв на стороне прокси). Подробности —
  [docs/10-architecture.md](docs/10-architecture.md) §2.
- **HTTP-таймаут клиента обязан превышать `timeout` у `getUpdates`**, иначе long polling
  вырождается в серию таймаутов.
- **`alembic` в контейнере видит миграции из ОБРАЗА, а не из смонтированного каталога.**
  Новая миграция не применится, пока образ не пересобран.
- **`postgres` требует `-c` и значение разными аргументами** в `command:`. Форма
  `-c=key=value` даёт `FATAL: unrecognized configuration parameter ""`, а кластер
  остаётся недоинициализированным: без базы и без строки в `pg_hba.conf`.
- **`pg_isready` не годится как healthcheck**: на сломанном кластере он рапортует
  `healthy`. Проверять реальным запросом к своей БД.
- **Healthcheck без проверки бывает двух видов, и оба одинаково бесполезны.** `worker`
  наследовал из образа `curl localhost:8000/health` и 103 проверки подряд числился
  `unhealthy`, работая нормально; у `bot` стояла заглушка `sys.exit(0)`, проходившая всегда.
  Процесс без порта проверяется пульсом — `core/heartbeat.py`, см. docs/80-deploy.md.
- **Список для выбора берётся с портала, своя таблица — только для уже выбранного.**
  `/bind` спрашивал таблицу `projects` (3 строки) вместо портала (15 групп), и человек
  видел неполный список без объяснения причины.
- **Живой список и кэш нельзя проверять по-разному.** Список задач берётся из Битрикса
  живьём, а `authorize_task_for_chat` смотрела только в `task_cache` — и карточка отвечала
  «задача не найдена» на задачу, которую сама же и показала строкой выше.
- **Молчаливое усечение выглядит как баг продукта.** Любой предел на количество строк или
  кнопок обязан быть виден в тексте: сколько показано, сколько всего.
- **Меню команд — обещание.** Команда в `setMyCommands`, которую роутер не знает, выглядит
  как поломка бота. Реестр один (`bot/commands.py`), из него строятся и меню, и `/help`,
  и тест-страж сверяет его с роутером.
- **Кнопка — то же обещание, но нарушает его правдоподобно.** Префикс `callback_data`
  был занят дважды (`p:` — и вариант ответа опросника, и выбор проекта), роутер
  разбирал первое, вторая ветка стояла ниже и была недостижима. Python о такой
  недостижимости молчит: это две одинаковые проверки подряд, а не мёртвый код после
  `return`. Человек в чате с двумя проектами видел «диалог устарел» — тот же текст,
  что у честно истёкшего токена. Реестр один (`bot/callbacks.py`), `callback_data`
  собирается только через него, страж сверяет обе стороны по исходнику.
- **В enum-поле Битрикса уходит ID элемента, а не подпись.** Запись подписи молча кладёт
  `0`: ошибки нет, задача создаётся, поле выглядит заполненным. Варианты списка видны
  только в `task.item.userfield.getlist`, в `getFields` их нет (docs/00-portal-facts.md §14).
- **Пользовательское поле задачи создаётся сразу для всего портала.** `ENTITY_ID=TASKS_TASK`,
  привязки к проекту не существует — и человеку это надо сказать до нажатия кнопки.
- **Схема и модель данных расходятся молча.** `answer_kind` и `options` были описаны в
  `20-data-model.md` с самого начала, а миграция `0007` их не создала. Вскрылось через
  неделю падением `column "options" does not exist`. Перед работой с таблицей — `\d` в
  psql, а не чтение документа.
- **Ответ человека нельзя терять молча.** Не подошёл полю — уходит в тело задачи вместе
  со строкой о том, что разобрать не удалось. Человек считает, что его услышали.
- **Справочник, который заполняется однократно, расходится с порталом молча.**
  `project_stages` писались только при импорте проекта. Владелец проекта заводил
  колонку в Битриксе — и её задачи попадали в сводке в строку «Вне канбана», то есть
  туда же, где честные `STAGE_ID=0`. Ни ошибки, ни отличия для человека. Любая копия
  чужих данных обязана иметь и обновление, и отметку времени этого обновления.
- **Одна строка на два разных смысла — это скрытая ошибка.** «Вне канбана» означало
  и «задача не разложена по колонкам» (норма), и «мы не знаем такой стадии» (наш
  разлад с порталом). Пока смыслы в одной строке, второй не виден никому.

## Работа с репозиторием

- **`.env` никогда не коммитится.** В нём сейчас входящий вебхук с правами администратора
  портала. `.gitignore` создан до `git init` — не ослаблять.
- Миграции — только через Alembic, только вперёд-совместимые: добавили колонку → заполнили →
  начали читать → следующим релизом убрали старое. Downgrade обязателен и проверяется тестом.
- Разработка идёт **сразу на боевом сервере** (решение заказчика). Значит: дамп БД перед
  каждой миграцией, сборка образов только в CI, `mem_limit` и `cpu_shares: 512` на всех
  контейнерах, feature-флаги на уровне теннанта для недоделанного.
- Соседи по VPS (`devon-website`, `mclick_landing`, `devon-billing`) не имеют лимитов ресурсов.
  Мы обязаны проигрывать им при конкуренции.

## Чек-лист перед коммитом

1. `ruff check` и `mypy --strict` чистые.
2. Тесты зелёные, включая тесты изоляции и безопасности.
3. Новая таблица — есть `tenant_id`, RLS, ретенция, запись в `20-data-model.md`.
4. Новая подстановка в текст — прошла через `esc_html`/`esc_bbcode`.
5. Новый вызов Битрикса — идёт через лимитер и правильный токен (`user` / `service_reader` /
   `service_admin`), мутация идемпотентна.
6. Новое действие пользователя — есть запись в аудит, высокорисковое помечено `high_risk`.
7. Секретов в diff нет.

**Выкатка идёт через GitHub Actions, руками на сервер ничего не копируется.**
Мердж в `main` → проверки → сборка образа в CI → публикация в GHCR → `scripts/deploy.sh`
по ssh. На сервере не собирается ничего; туда едут `docker-compose.yml`, два скрипта
и тег образа. Подробности, секреты репозитория и откат — docs/80-deploy.md §8.

Всё, что ниже до конца раздела, — **история и аварийный путь** на случай, когда
GitHub недоступен. Три записанные здесь аварии (tar не обновляет существующие файлы;
`.claude/` рвёт поток; две сессии затирают друг друга) устранены не аккуратностью,
а тем, что этого шага в выкатке больше нет.

Синхронизация кода на сервер — tar по ssh, репозитория на сервере нет:

```bash
tar --exclude='./.claude' --exclude='./.git' --exclude='.env' --exclude='__pycache__' --exclude='.pytest_cache' --exclude='.ruff_cache' --exclude='.mypy_cache' --exclude='./backups' -czf - . | ssh -i ~/.ssh/id_ed25519 root@91.142.94.189 'cd /opt/b24sdbot && tar -xzf -'
```

**`.claude/` исключать обязательно.** Там лежат рабочие каталоги агента — полные
чекауты этого же репозитория на других ветках, 114 МБ. Без исключения tar читает
их вместе с меняющимся `.mypy_cache`, ловит `file changed as we read it`, рвёт поток
на середине, и на сервер приезжает половина дерева. Добавлено в `.gitignore`.

**tar только добавляет файлы, но никогда не удаляет.** Файл, которого больше нет
в репозитории, останется на сервере навсегда и попадёт в образ. Если дерево на сервере
разошлось — `rm -rf src tests migrations docs` перед распаковкой.

**Распаковывать с `--overwrite`.** 16.08 синхронизация без него создала новые файлы,
но не обновила ни одного существующего: на сервере остался старый `main.py`, образ
собрался без мини-аппа, а `docker compose ps` при этом показывал `healthy`. Молчаливо
и правдоподобно. **После синхронизации сверять контрольные суммы**, не полагаясь
на код возврата:

```bash
for f in $(find src migrations -name '*.py'|sort); do printf "%s %s\n" "$(sed 's/\r$//' "$f"|md5sum|cut -d' ' -f1)" "$f"; done
```

`sed` здесь обязателен: локальное дерево на Windows хранит CRLF, серверное — LF,
и без нормализации различаются все файлы разом.

**Сервер один, а сессий может быть несколько.** 16.08 две сессии выкатывались
одновременно и по очереди затирали друг друга: `docker compose up` падал с
`No such container`, а собранный образ подменялся чужим. Перед выкаткой свериться:

```bash
ssh -i ~/.ssh/id_ed25519 root@91.142.94.189 "find /opt/b24sdbot/src -newermt '-8 minutes'; docker image inspect b24sdbot-api --format '{{.Created}}'"
```

```bash
ssh -i ~/.ssh/id_ed25519 root@91.142.94.189 'cd /opt/b24sdbot && docker compose build api bot worker && docker compose up -d --force-recreate api bot worker && docker compose ps'
```

**`.env` на сервере не перезаписывается синхронизацией и не существует локально.**
Там боевые секреты: `DATABASE_URL`, `MASTER_KEY`, `B24_CLIENT_SECRET`, входящий вебхук
с правами администратора портала.

| Отчёт | свод по статусам, свод по стадиям, итог; обе суммы обязаны совпасть с итогом |

Четыре факта портала, добытые перед тем, как писать код (docs/00-portal-facts.md §5.2):

1. **`TIME_SPENT_IN_LOGS` у задачи заполнен** и равен сумме её списаний в секундах
   (задача `#17` — `'18000'`). У задачи без списаний приходит `null`. Значит для строки
   в карточке второй запрос не нужен вовсе.
2. **Постраничность `task.elapseditem.getlist` сломана.** `start=50` возвращает ту же
   первую страницу (ID `1, 3, 5`), `NAV_PARAMS` в обеих формах даёт ноль записей. При этом
   конверт честно пишет `next: 50, total: 79`.
3. **`ORDER` работает** — единственный доступный рычаг. Поэтому список берётся с двух
   концов (`DESC` и `ASC`), объединяется по `ID`, и размер объединения сверяется с `total`.
   Сошлось — данные полные; не сошлось — в отчёте стоит строка «портал отдал N из M,
   сумма это минимум». Полноту по датам доказать нельзя: запись заводится задним числом.
4. **Считать надо по `DATE_START`**, а не по `CREATED_DATE`: первое — когда работали,
   второе — когда занесли, и при списании задним числом они расходятся.

Три решения, которые видно в коде:

- **Стадии сводятся по названию, а не по id.** У каждого проекта свой канбан со своими
  идентификаторами; в чате с двумя проектами «Сделаны» иначе встали бы двумя строками.
  Проверено на живых данных: у теннанта два проекта с одинаковыми названиями колонок.
- **Месяц берётся из самой отметки времени** (`entry.at.year/month`), а не приведением
  к UTC: 31 декабря 23:30 по Москве иначе уехало бы в следующий год.
- **Кэш снимка на 5 минут.** Месяцы листают кнопками подряд, и каждый следующий — срез
  того же снимка, а не новый поход в портал.

В клиенте появился `call_total`: `total` живёт в конверте ответа, а `call` отдаёт только
`result`, и без него нельзя отличить «показали всё» от «показали первые 50 из трёхсот».

Шесть вещей, которые определили форму кода:

1. **Кнопка в группе работает и тогда, когда личка недоступна.** Нажатие инлайн-кнопки
   не требует диалога с ботом — поэтому эскалация недоставки несёт те же
   «Подтвердить»/«Отклонить» с `owner_tg_id` ответственного. Это не украшение, а
   единственный способ принять решение, ни разу не открыв личку, в которую сообщение
   и не дошло. Чужое нажатие отсекает `consume_token`, как и везде.
2. **Отметка «отправлено» ставится ДО отправки.** Условие («срок через два часа»)
   истинно всё окно целиком, и без отметки каждый проход слал бы одно и то же. Цена
   отметки до — одно потерянное напоминание; цена отметки после — поток одинаковых
   сообщений, пока Telegram отвечает ошибкой. `outbox.dedup_key` эту роль не выполняет:
   его уникальный индекс накрывает только `pending`/`sending`.
3. **Сводка — только числа, без заголовков задач.** Собрана сервисным токеном, то есть
   видит больше читателя чата. Подробности открываются кнопкой, а она уже работает под
   личным токеном нажавшего. Тем же объясняется, почему `/digest` считает то же самое
   токеном спросившего: числа могут честно отличаться от утренних, и это свойство прав.
   Проверяется тестом `test_digest_never_shows_task_titles`.
4. **Сводка молчит, когда сообщать нечего.** Ежедневное «всё по сроку» — шум, который
   перестают читать вместе со всем остальным. Отметка при этом ставится: вопрос на
   сегодня решён. `/digest` отвечает всегда — там спросил человек.
5. **«Срок сегодня» считается по местному дню портала.** В 23:00 по Москве календарные
   сутки UTC и местные расходятся, и именно в эти часы строка читается буквально.
   Ради этого в зависимости добавлен `tzdata`: `python:3.12-slim` базы часовых поясов
   не гарантирует, а `ZoneInfo('Europe/Moscow')` без неё бросает исключение. Колонка
   `tenants.tz` существовала с миграции `0001` и до сих пор не читалась ни разу.
6. **Шаги цепочки не складываются.** Воркер, пролежавший сутки, иначе прислал бы
   напоминание и эскалацию одной пачкой — то есть шум ровно там, где мы с ним боремся.
   За проход по одному запросу уходит не больше одного сообщения.
